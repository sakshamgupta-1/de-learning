Can it keep up?

Enter your stream's numbers. The calculator works out each batch's size and duration, whether the stream keeps up, and how long a backlog (say after an outage) takes to clear.

A simplified model: processing scales linearly with cores, and overhead (planning, discovery, commits) is fixed per batch. Real rates vary with data, skew and state; measure processedRowsPerSecond to calibrate "rows/s one core processes".

A metrics listener

from pyspark.sql.streaming import StreamingQueryListener
import json

class MetricsListener(StreamingQueryListener):
    def onQueryStarted(self, event):
        emit("stream.started", {"name": event.name, "id": str(event.id)})

    def onQueryProgress(self, event):
        p = json.loads(event.progress.json)
        emit("stream.progress", {
            "name": p["name"], "batch": p["batchId"],
            "input_rps": p.get("inputRowsPerSecond", 0),
            "processed_rps": p.get("processedRowsPerSecond", 0),
            "batch_ms": p["durationMs"].get("triggerExecution", 0),
            "state_rows": sum(s["numRowsTotal"] for s in p.get("stateOperators", [])),
            "dropped_late": sum(s.get("numRowsDroppedByWatermark", 0) for s in p.get("stateOperators", [])),
        })

    def onQueryIdle(self, event):        # Spark 3.5+: no new data
        pass

    def onQueryTerminated(self, event):
        emit("stream.terminated", {"id": str(event.id), "error": event.exception})

spark.streams.addListener(MetricsListener())

emit stands for your metrics client (a Delta table, Prometheus push gateway, CloudWatch, Datadog). Keep it fast and non-blocking: the listener runs on the driver for every batch of every query. Name queries with .queryName("orders_gold") so metrics are readable.

Replay recipes

Kafka: new checkpoint from explicit offsets

start = json.dumps({"orders": {"0": 15000, "1": 15000, "2": 15000}})   # a little before the last good point
(spark.readStream.format("kafka").option("subscribe", "orders")
      .option("startingOffsets", start) …
      .writeStream.option("checkpointLocation", "/chk/orders_v2")          # new checkpoint
      .foreachBatch(idempotent_merge).start())

Delta source: new checkpoint from a version

spark.readStream.option("startingVersion", 4120).table("bronze.orders")

Auto Loader: new checkpoint, only recent files

(spark.readStream.format("cloudFiles")
      .option("cloudFiles.format", "json")
      .option("modifiedAfter", "2026-10-30T00:00:00Z")   # skip files before the cut-over
      .load("s3://landing/orders/"))

Recompute a range in batch, stream untouched

fixed = transform(spark.read.table("bronze.orders")
                       .where("order_date BETWEEN '2026-10-01' AND '2026-10-07'"))
(fixed.write.format("delta").mode("overwrite")
      .option("replaceWhere", "order_date BETWEEN '2026-10-01' AND '2026-10-07'")
      .saveAsTable("silver.orders"))

Run the range recompute while the stream keeps writing newer dates. If the stream could write into the same range at the same time (late data), use a MERGE keyed on the business key instead of replaceWhere.
