Running streams at scale

Six problems that appear once streams run for months: falling behind, small files, hot partitions, duplicates from reprocessing, crowded clusters and cost. Each follows symptom → why → confirm → fix → prevent → interview answer.

Falling behind

Symptom

Lag grows every hour; batch duration climbs above the trigger interval; data in the target is increasingly stale.

Why it happens

Processing rate is below input rate: input grew, a stage got slower (state, skew, a heavier MERGE), or the cluster shrank. Each batch then takes more data, which makes it slower still.

How to confirm

  1. processedRowsPerSecond below inputRowsPerSecond across many batches.
  2. The durationMs breakdown shows where the time goes: before tasks (latestOffset, queryPlanning), in the job and sink (addBatch), or commits.
  3. Within addBatch, the Spark UI shows the slow stage, as for any job (debug flow).

Fix

  • Fix the slow part first: skew, state size, MERGE pruning, discovery mode.
  • Add parallelism: more cores, more Kafka partitions or minPartitions.
  • Rate-limit batches (maxOffsetsPerTrigger) so a backlog drains in steady batches instead of one huge one.

Prevent

  • Alert on lag in minutes and on processing below input; size for peak plus catch-up headroom (calculator).
Say it in an interview
"If processing rate is below input rate the stream falls further behind each batch. I use the duration breakdown to find whether it's discovery, the job, state or the sink, fix that, and rate-limit so catch-up happens in steady batches."

Small files from frequent batches

Symptom

Streaming tables have hundreds of thousands of small files; downstream reads and MERGEs slow down over weeks.

Why it happens

Every micro-batch writes at least one file per task. Short triggers and many shuffle partitions multiply that.

How to confirm

  1. DESCRIBE DETAIL: numFiles high, average size in KB.

Fix

  • Optimized writes and auto-compaction on the table; scheduled OPTIMIZE.
  • Longer trigger interval, or availableNow on a schedule; fewer output partitions for small batches.

Prevent

  • Set compaction properties when creating streaming tables (small files).
Say it in an interview
"Micro-batches write small files by nature, so every streaming table gets optimized writes and auto-compaction, and I pick the trigger interval with file sizes in mind."

A hot Kafka partition

Symptom

Every batch has one task far longer than the others; lag sits on one partition.

Why it happens

Producers key by a value with a dominant key (one large customer, a null key routed to one partition), so one partition gets most of the traffic. Spark reads one task per partition by default.

How to confirm

  1. Per-partition offsets growth in Kafka; the Spark UI task timeline shows one long read task.

Fix

  • minPartitions above the partition count so Spark splits the big partition's range across tasks.
  • Repartition after reading if downstream work is the heavy part.
  • With producers: a better key, or more partitions.

Prevent

  • Review partition keys when topics are designed; monitor per-partition throughput.
Say it in an interview
"A hot Kafka partition becomes one slow task per batch. On the Spark side minPartitions splits it; the real fix is the producer's partition key."

Duplicates after reprocessing

Symptom

After restarting a stream with a new checkpoint, the target has duplicates around the restart point, or for the whole history.

Why it happens

A new checkpoint has no memory of what was written. Starting earlier than the last written point (safe for completeness) writes the overlap again into an append-only target.

How to confirm

  1. Duplicates by business key share an ingestion time from the reprocessing run.

Fix

  • Deduplicate the target for the overlap window.
  • Write reprocessing runs with MERGE on the business key, or into a fresh table that replaces the old one.

Prevent

  • Design targets so a replay is harmless: business keys, MERGE or replaceWhere by range, and a written replay runbook (decision path).
Say it in an interview
"A new checkpoint forgets what was written, so I start a bit early for safety and make the write idempotent with a MERGE on the business key, or rebuild into a new table and swap."

Too many streams on one cluster

Symptom

A cluster running dozens of queries has slow batches across all of them, while executors are mostly idle; the driver is at high CPU or memory.

Why it happens

Each query plans and commits every batch on the driver, and the driver also runs every listener. Many queries with short triggers overload the driver even when executor work is small.

How to confirm

  1. Driver CPU and GC high; queryPlanning and commit durations high for every query.

Fix

  • Spread queries over more clusters or jobs; lengthen triggers; use scheduler pools so queries share executors fairly.
  • Consolidate similar streams (one query over several topics with subscribePattern) where semantics allow.

Prevent

  • Budget queries per driver, and watch driver metrics, not just executor metrics.
Say it in an interview
"With many streams on one cluster the driver becomes the bottleneck, because it plans and commits every batch of every query. I spread queries out, lengthen triggers and watch driver load."

Runaway cost

Symptom

Streaming compute is the largest line in the bill, though most streams carry little data most of the day.

Why it happens

Always-on clusters, sized for peak, for streams whose consumers only need hourly or daily freshness.

How to confirm

  1. Cluster utilisation and records per hour per stream against their real freshness requirement.

Fix

  • Move low-urgency streams to availableNow on a schedule, keeping their checkpoints.
  • Group small streams on shared clusters or in one Lakeflow pipeline with enhanced autoscaling.
  • Right-size: smaller, fewer workers for low-volume streams.

Prevent

  • Set a freshness SLA per stream at design time and choose the trigger from it; review cost per stream regularly.
Say it in an interview
"I set a freshness requirement per stream and choose the trigger from it. Anything that tolerates minutes of delay runs as availableNow on a schedule: same incremental semantics, but the cluster is off most of the time."
