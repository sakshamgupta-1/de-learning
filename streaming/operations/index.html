Keeping streams fast, visible and recoverable

A stream is a long-running system: it has to keep up with its input, tell you when it doesn't, and survive code changes and bad data. This module covers performance bottlenecks, what to monitor, and how to replay or reprocess safely. A 10-minute refresher.

Keeping up: input rate vs processing rate

A stream is healthy when it processes data at least as fast as it arrives, with headroom for bursts and catch-up after failures. Two numbers from every batch tell you: input rate (rows per second arriving) and processing rate (rows per second processed). If processing is below input for long, the backlog grows, batches get bigger and slower, and latency climbs.

Replay and reprocessing: a decision path

Most "can I just restart it?" questions come down to whether the checkpoint is still valid for the new code. Answer the questions in order; a "yes" gives the playbook.

Common trap
Changing startingOffsets, startingVersion or modifiedAfter on an existing checkpoint does nothing: those options apply only when a query starts with a new checkpoint. Reprocessing always means either a new checkpoint or a separate batch job.

Cost

  • Always-on vs scheduled: a continuously running cluster costs the same at 3 a.m. as at peak. If minutes of latency are acceptable, availableNow on a schedule processes the same data incrementally and shuts down (compare triggers).
  • Many small streams: run several queries on one cluster (each with its own checkpoint), or a Lakeflow pipeline, instead of a cluster per stream.
  • Batch size: tiny frequent batches pay fixed overhead each time and create small files; longer intervals are usually cheaper per row.
  • Autoscaling on always-on streams is tricky: classic autoscaling reacts to task backlog within a batch, not to stream lag. Databricks' enhanced autoscaling in Lakeflow pipelines is designed for streaming load.

Say it in an interview

Bottlenecks
"I compare input rate with processing rate and batch duration with the trigger interval. If it's falling behind, the progress metrics show where the batch spends its time: planning and discovery, the processing stages, state commits, or the sink. Then it's the usual Spark tuning: parallelism, skew, state size, and a sink that prunes."
Monitoring
"Every stream gets a listener that ships progress metrics, and alerts on freshness, lag in minutes, processing rate below input rate, state growth and dropped late rows, plus query failures. Job status alone misses a stream that's running but falling behind."
Reprocessing
"First I ask whether the checkpoint is still valid. Stateless changes restart on the same checkpoint. Source or stateful changes need a new checkpoint with an explicit starting point and a state rebuild. To fix output already written, I recompute the affected range in batch with replaceWhere or MERGE and leave the stream running."

Quick check

Batch duration is 4 minutes with a 1-minute trigger. What's happening, and what do you check first?
The stream is falling behind: each batch picks up more data than the last. Check the duration breakdown in the progress metrics to see where time goes, then processing rate vs input rate, task count and skew in the Spark UI, and state and sink time.
You fixed a bug in a filter. Can you restart on the same checkpoint?
Yes: filters and projections are stateless changes. But only new data gets the fix; output already written stays wrong until you recompute that range separately.
You changed a groupBy key. What now?
The state's schema no longer matches, so you need a new checkpoint. Rebuild state by reprocessing enough history (from Bronze or the source's retention), then switch the target over or overwrite the affected range.
What does a full refresh of a Lakeflow streaming table do?
It clears the table's data and its checkpoints and reprocesses everything still available in the source. It's convenient, but it only works if the source still has all the history (Kafka retention, for example, may not).
