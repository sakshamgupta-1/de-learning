A stream is a table that keeps growing

Structured Streaming runs your DataFrame query again and again on new data, as a series of small batch jobs. Know the micro-batch loop, triggers, output modes and checkpoints, and most streaming interview questions become batch questions you already know. A 10-minute refresher.

The model: an unbounded input table

Structured Streaming treats a stream as an input table that only grows. You write an ordinary DataFrame query against it. Spark runs that query incrementally: each run reads only the rows that arrived since the last run, updates any running state, and writes the change to a sink.

By default each run is a micro-batch: a normal Spark job with the same Catalyst plan, stages and tasks you know from Spark Core. The streaming engine adds three things on top: deciding which new data goes in each batch, remembering progress in a checkpoint, and carrying state between batches for aggregations, deduplication and joins.

(spark.readStream.format("kafka")                    # source: where new rows come from
      .option("kafka.bootstrap.servers", brokers).option("subscribe", "orders").load()

      .trigger(processingTime="1 minute")            # when to run the next micro-batch

The micro-batch loop, and why a crash doesn't duplicate data

Every micro-batch follows the same five steps. The order matters: the batch's input range is written down before any work starts, and the batch is marked done only after the sink write succeeds. Step through a normal batch, then a crash.

The sink "remembers" batch N because the Delta sink records the query id and batch id in each commit, so a replayed batch is skipped. That's why the sink choice matters for exactly-once: see below.

The trigger changes when work runs, not what the query means. The same query and checkpoint can move between processingTime and availableNow as cost and latency needs change.

Checkpoints and exactly-once

End-to-end exactly-once needs three things together. Remove any one and you get at-least-once (duplicates after a failure) or data loss.

  1. A replayable source that can re-read a given range: Kafka offsets, file lists, Delta table versions.
  2. A checkpoint that records each batch's range before processing (offset log) and its completion after (commit log), plus any state.
  3. An idempotent sink, so rewriting a replayed batch has no effect: the Delta and file sinks track batch ids. foreachBatch and the Kafka sink are at-least-once unless you make the write idempotent yourself.
Common trap
A checkpoint belongs to one query. Two queries sharing a checkpoint location corrupt each other's progress; copying a checkpoint to a different query or sink isn't supported. One query, one checkpoint, kept as long as the query lives.

Say it in an interview

How it works
"Structured Streaming treats the stream as an unbounded table and runs my DataFrame query incrementally in micro-batches. Each batch is a normal Spark job. Before it runs, Spark writes the batch's input range to the offset log in the checkpoint; after the sink write succeeds, it writes the commit log. On restart, any batch that has an offset entry but no commit is re-run with exactly the same range."
Exactly-once
"Exactly-once is end to end: a replayable source like Kafka or Delta, the checkpoint, and an idempotent sink. The Delta sink records the batch id, so a replayed batch is skipped. With foreachBatch I make the write idempotent myself, with a MERGE or Delta's txnAppId and txnVersion options."
Triggers and cost
"For most ingestion I use availableNow on a schedule: it processes the backlog with streaming's incremental guarantees and then shuts down, so I don't pay for an idle cluster. I keep a continuously running query with a processing-time trigger only where minutes of latency matter."

Quick check

What's the difference between once and availableNow?
Both process what's available and stop. once does it in a single batch and ignores rate limits like maxFilesPerTrigger, so a large backlog becomes one huge batch. availableNow splits it into several batches that respect those limits. once is deprecated.
A count-by-key query fails with "Append output mode not supported". Why, and what are the options?
Append writes rows that never change, but a running count changes every batch. Use update (with an upsert sink) or complete (small results), or add a watermark and a window so each window's count is final once the watermark passes it.
The job crashed after writing to the sink but before the commit log. What happens on restart?
The batch has an offset entry but no commit, so Spark re-runs it with the same input range. A Delta or file sink sees the batch id was already written and skips it; a non-idempotent foreachBatch write would duplicate it.
Is a stream-static join stateful?
No. Each micro-batch joins its new rows with the static table, read at that batch (a Delta static side picks up its latest version each batch). Nothing is carried between batches. Stream-stream joins are stateful.
Can you change spark.sql.shuffle.partitions for a running stateful query?
Not with the same checkpoint: the state is already split into that many partitions, and Spark keeps the original number. Changing it needs a new checkpoint (and so a state rebuild or reprocessing).
