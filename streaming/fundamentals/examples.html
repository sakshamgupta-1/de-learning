Three triggers, ten minutes

Data arrives steadily. Press Play to see when each trigger runs batches and how long the cluster is up. The point to notice: availableNow on a schedule trades latency for a cluster that's off most of the time.

Orange: a micro-batch · grey band: cluster running · blue: cluster start-up. Timing is illustrative, not a benchmark.

The same query, three triggers

q = (spark.readStream.table("bronze.orders")
          .where("status IS NOT NULL")
          .writeStream
          .option("checkpointLocation", "/chk/silver_orders"))

q.trigger(processingTime="2 minutes").toTable("silver.orders")   # always on, a batch every 2 min
q.trigger(availableNow=True).toTable("silver.orders")            # run from a scheduled job; stops when caught up
q.toTable("silver.orders")                                        # default: next batch as soon as the last ends

Pick one per run; they can share the checkpoint across runs because it tracks data positions, not the trigger. With availableNow, wait for the query to finish before the job ends: query.awaitTermination().

Output modes in code

counts = events.groupBy("customer_id").count()

# complete: whole table every batch, fine for small results
counts.writeStream.outputMode("complete").format("delta") \
      .option("checkpointLocation", "/chk/c1").toTable("gold.counts_full")

# update: changed keys only; the Delta sink doesn't upsert, so MERGE in foreachBatch
def upsert(batch, batch_id):
    (DeltaTable.forName(spark, "gold.counts").alias("t")
        .merge(batch.alias("s"), "t.customer_id = s.customer_id")
        .whenMatchedUpdateAll().whenNotMatchedInsertAll().execute())

counts.writeStream.outputMode("update").foreachBatch(upsert) \
      .option("checkpointLocation", "/chk/c2").start()

# append: needs a watermark and a window, so each window is written once it's final (Module 2)
(events.withWatermark("event_ts", "10 minutes")
       .groupBy(F.window("event_ts", "5 minutes"), "customer_id").count()
       .writeStream.outputMode("append").format("delta")
       .option("checkpointLocation", "/chk/c3").toTable("gold.counts_5m"))

Idempotent foreachBatch

A replayed batch arrives with the same batch_id. Use it, so writing it twice changes nothing.

APP_ID = "silver_orders_writer"            # stable per query; don't reuse across queries

def write_two_tables(batch, batch_id):
    batch.persist()                          # two writes from one batch (classic compute only)
    try:
        (batch.where("region = 'EU'").write.format("delta")
              .option("txnAppId", APP_ID).option("txnVersion", batch_id)
              .mode("append").saveAsTable("silver.orders_eu"))
        (batch.where("region = 'US'").write.format("delta")
              .option("txnAppId", APP_ID).option("txnVersion", batch_id)
              .mode("append").saveAsTable("silver.orders_us"))
    finally:
        batch.unpersist()
  • Delta skips a write when that table has already committed this txnAppId at this or a later txnVersion.
  • On Databricks serverless, persist() isn't available: drop it and accept two scans of the batch, or write once and split downstream.
  • For upserts, deduplicate the batch by key before MERGE (full pattern).

Stream-static join (stateless)

customers = spark.read.table("silver.customers")      # static side: a Delta table
enriched = (spark.readStream.table("bronze.orders")
                 .join(customers, "customer_id", "left"))

Each micro-batch joins its new orders to the customers table as it is at that batch: a Delta static side is re-read at its latest version every batch, so updates to customers show up without restarting. Nothing is kept in state. Orders that arrived before a customer change aren't re-joined; if that matters, it's a stream-stream join or a later reconciliation (Module 2).

Watching a running query

q = df.writeStream.option("checkpointLocation", chk).toTable("silver.orders")

q.id, q.runId          # id is stable across restarts; runId changes each start
q.status               # {'message': 'Waiting for data to arrive', 'isDataAvailable': False, …}
q.lastProgress         # metrics for the last batch, as a dict
q.recentProgress       # the last few progress reports
q.exception()          # the error if the query stopped with one
spark.streams.active   # all running queries in this session
