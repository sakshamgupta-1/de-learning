When streams misbehave

Five failures that come from the basics: the micro-batch loop, checkpoints, triggers and output modes. Each follows symptom → why → confirm → fix → prevent → interview answer.

Duplicates after a restart

Symptom

After a failure or redeploy, the target has some rows twice, always in batch-sized groups.

Why it happens

The batch in flight is replayed on restart. A Delta or file sink skips it; foreachBatch, the Kafka sink and foreach don't, so a plain append or INSERT runs twice.

How to confirm

  1. Group the duplicates by ingestion time or batch: they cluster around the restart.
  2. Check the sink: is the write inside foreachBatch, to Kafka, or to an external database?

Fix

  • Delta inside foreachBatch: pass txnAppId and txnVersion=batch_id.
  • Upserts: deduplicate the batch by key, then MERGE.
  • Kafka sink: make consumers idempotent (dedupe on a key), since the Kafka sink is at-least-once.
  • Clean the existing duplicates with a one-off dedup.

Prevent

  • Treat every foreachBatch as "will be called twice with the same batch id" in code review, and test it by killing a query mid-batch.
Say it in an interview
"The batch in flight is always replayed on restart, so exactly-once depends on the sink. Delta sinks skip replays by batch id; for foreachBatch I make the write idempotent with txnAppId and txnVersion, or a MERGE on a deduplicated batch."

A lost, deleted or shared checkpoint

Symptom

After someone "cleaned up" a folder, the stream either reprocesses everything from the start, or silently skips data. Or two jobs keep failing with conflicting batch errors.

Why it happens

  • Without a checkpoint, a query starts fresh from its starting position: Kafka's default startingOffsets is latest, so data in between is skipped; file and Auto Loader sources reprocess every existing file.
  • Two queries writing to one checkpoint location overwrite each other's offset and commit logs.

How to confirm

  1. Check the checkpoint path still has offsets/ and commits/ with recent batch ids.
  2. Search job definitions for the same checkpointLocation used twice.
  3. Compare the query id before and after: a new id means a new checkpoint.

Fix

  • Restore the checkpoint from storage versioning or backup if possible.
  • Otherwise restart deliberately: set startingOffsets (Kafka), startingVersion (Delta source) or modifiedAfter (Auto Loader) to the last processed point, and dedupe the overlap (replay playbook).
  • Give each query its own checkpoint.

Prevent

  • Derive checkpoint paths from the target table name; keep them out of folders that lifecycle rules or clean-up jobs touch; restrict delete permissions.
Say it in an interview
"The checkpoint is the stream's memory: losing it means the source decides where to start, which for Kafka defaults to latest and skips data. I keep one checkpoint per query, protected from clean-up, and if one is lost I restart from an explicit position and dedupe the overlap."

A huge first batch

Symptom

A new stream, or one restarted after a long pause, runs one enormous batch that spills, runs out of memory or takes hours. Later batches are fine.

Why it happens

Without rate limits, the first batch takes everything available: all of a Kafka topic from earliest, every existing file in a folder, or a long backlog. The deprecated once trigger ignores rate limits entirely.

How to confirm

  1. lastProgress["numInputRows"] for batch 0 is orders of magnitude above later batches.
  2. The source options have no maxOffsetsPerTrigger / maxFilesPerTrigger / maxBytesPerTrigger.

Fix

  • Set a rate limit so the backlog is processed in many right-sized batches.
  • Use availableNow rather than once.
  • For very large histories, backfill with a batch job, then start the stream from the end of the backfill.

Prevent

  • Always set a rate limit on Kafka and file sources; size it so one batch finishes well inside the trigger interval.
Say it in an interview
"The first batch of a new stream takes the whole backlog unless I set maxOffsetsPerTrigger or maxFilesPerTrigger. I always set one, use availableNow instead of once, and backfill large histories separately."

"Append output mode not supported"

Symptom

The query fails at start with AnalysisException: Append output mode not supported when there are streaming aggregations on streaming DataFrames/DataSets without watermark.

Why it happens

Append writes only rows that will never change. An aggregation without a watermark can always change, so Spark can't know when a row is final.

How to confirm

  1. The plan has an aggregation (groupBy or a window) and no withWatermark on its event-time column.

Fix

  • Add withWatermark and group by a time window, so append writes each window once it closes.
  • Or use update mode with foreachBatch + MERGE, or complete mode for small results.

Prevent

  • Decide the output mode when designing the query, from what the target needs: final rows (append + watermark) or current values (update + MERGE).
Say it in an interview
"Append needs to know when a row is final. With an aggregation that comes from a watermark and a window; otherwise I use update mode and MERGE into the target."

The job finishes but the stream stopped

Symptom

A scheduled job reports success after seconds, but no data was written. Or a long-running stream died hours ago and nothing alerted.

Why it happens

  • start() returns immediately; if the script ends, the application stops the query with it.
  • A query that throws stops on its own; unless something checks it, the cluster or job may look healthy.

How to confirm

  1. The driver log shows the query starting and the application exiting right after.
  2. spark.streams.active is empty; q.exception() holds the error.

Fix

  • End the script with q.awaitTermination() (or spark.streams.awaitAnyTermination() for several queries) so failures fail the job.
  • Let the job's retry policy restart failed streams.

Prevent

  • Alert on query failure and on freshness (time since last batch), not only on job status (monitoring).
Say it in an interview
"start() is non-blocking, so a job needs awaitTermination to surface failures. In production I run streams as jobs with retries and alert on freshness and query failures, not just job status."
