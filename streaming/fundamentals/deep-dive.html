What's in a checkpoint

/chk/orders_bronze/
├─ metadata              the query id (a UUID that survives restarts)
├─ offsets/              write-ahead log: one file per batch, written BEFORE the batch runs
│  ├─ 41
│  └─ 42                 batch 42's end offsets per source, plus key confs (shuffle partitions, …)
├─ commits/              one file per batch, written AFTER the sink succeeds
│  └─ 41                 → batch 42 is "planned but not committed"
├─ sources/0/            source-specific progress (e.g. the file source's list of files seen;
│                        Auto Loader keeps a RocksDB of discovered files here)
└─ state/0/              stateful operator 0, one folder per state partition
   ├─ 0/  1.delta 2.delta … 10.snapshot      (default provider)
   └─ …                                        (RocksDB provider: SST and changelog files)

An offsets file for a Kafka source looks like this (trimmed). The first line is the format version; the next carries the batch watermark, timestamp and the configurations that must stay fixed for this checkpoint; then one line per source:

v1
{"batchWatermarkMs":0,"batchTimestampMs":1761900000000,"conf":{"spark.sql.shuffle.partitions":"200", …}}
{"orders":{"0":15200,"1":15188,"2":15231}}
  • Why the confs are stored: state is partitioned by them. On restart Spark restores spark.sql.shuffle.partitions from the checkpoint, whatever the session says.
  • Retention: Spark keeps the last spark.sql.streaming.minBatchesToRetain (100) batches of logs and state versions, and deletes older ones in the background.
  • Where it lives: durable, consistent storage (cloud object storage or HDFS), never local disk. On Databricks with Unity Catalog, a volume or external location.

The source and sink contracts

Source

  • Reports its latest available offset.
  • Returns the data between any two offsets, the same data every time (replayable).
  • Is told when offsets are committed, so it can discard old data if it wants.

Kafka, files, Delta, Auto Loader: replayable. The socket and rate test sources aren't production sources.

Sink

  • Receives each batch with its batch id.
  • Must make writing the same batch id twice have no effect (idempotent).

Delta and file sinks: idempotent (batch ids recorded in the Delta log or _spark_metadata). Kafka sink, foreach, foreachBatch: at-least-once unless you make them idempotent.

Making foreachBatch idempotent

  • Delta writes: pass txnAppId (a stable id for this query) and txnVersion (the batch id). Delta skips a write whose app id and version it has already committed.
  • MERGE: naturally idempotent for upserts if the batch is deduplicated by key first: re-running it updates rows to the same values.
  • External systems: write with the batch id and skip batch ids already applied, or use upserts keyed on a natural key.

Examples in code: idempotent foreachBatch.

Trigger edge cases

  • Overrunning batches: with processingTime="1 minute", a batch that takes 90 seconds is followed immediately by the next. Batches never overlap, so a query that's always overrunning is falling behind (Module 4).
  • Empty batches: if no new data arrived, no batch runs, except that a stateful query may run a no-data batch to advance the watermark and emit or evict state (spark.sql.streaming.noDataMicroBatches.enabled, true by default).
  • availableNow and rate limits: it fixes the end position at start-up, then works through it in batches sized by maxFilesPerTrigger / maxOffsetsPerTrigger. Data arriving during the run waits for the next run.
  • Switching triggers on the same checkpoint is fine: the checkpoint records data positions, not the trigger.
  • Databricks serverless supports only availableNow (and the deprecated once) in notebooks and jobs; Lakeflow pipelines manage their own triggers.

Continuous processing

trigger(continuous="1 second") starts long-running tasks that read and write continuously, with checkpoints every interval. Latency drops to about a millisecond, at a cost:

  • Only map-like operations (select, filter, projections); no aggregations, joins between streams or dropDuplicates.
  • At-least-once, not exactly-once.
  • Kafka and the rate source in, Kafka, memory and console out.
  • It's been experimental since Spark 2.3. In interviews, mention it exists and why it's rarely used; micro-batches with a short or default trigger cover most low-latency needs.

The id stays the same across restarts from the same checkpoint; the runId changes on every start. Use the id to join metrics across restarts.

Check yourself

Why is the offset log written before the batch runs, rather than after?
So that after a crash Spark knows exactly which range the unfinished batch covered and can re-run that same range. If it wrote offsets afterwards, a crash mid-batch would leave Spark to plan a new, possibly different range, and an idempotent sink could no longer recognise the replay.
Your foreachBatch writes to Postgres with INSERT. After a restart you see duplicates. Fix?
foreachBatch is at-least-once. Make the write idempotent: upsert on a natural key (INSERT … ON CONFLICT DO UPDATE), or store the last applied batch id in the target and skip batches already applied.
Does a stateless query ever run a batch with no new data?
No. No-data batches exist so stateful queries can advance the watermark and emit or drop state; a stateless query has nothing to do without new data.
