Windowed counts with a watermark

from pyspark.sql import functions as F

orders = spark.readStream.table("bronze.orders")            # has order_ts (event time)

per_10m = (orders
    .withWatermark("order_ts", "15 minutes")                 # accept up to 15 min late
    .groupBy(F.window("order_ts", "10 minutes"), "store_id")
    .agg(F.count("*").alias("orders"), F.sum("amount").alias("revenue"))
    .select(F.col("window.start").alias("window_start"),
            F.col("window.end").alias("window_end"), "store_id", "orders", "revenue"))

(per_10m.writeStream.outputMode("append")                     # each window written once, when final
        .option("checkpointLocation", "/chk/gold_orders_10m")
        .toTable("gold.orders_10m"))
  • Rows for a window appear about 10 + 15 minutes after the window starts: its length plus the watermark delay.
  • Sliding version: F.window("order_ts", "10 minutes", "5 minutes"). Each order is then counted in two windows.
  • Need results sooner? Use outputMode("update") with a MERGE sink: partial counts are visible every batch and corrected as late data arrives.

Session windows

sessions = (clicks
    .withWatermark("click_ts", "30 minutes")
    .groupBy(F.session_window("click_ts", "20 minutes"), "user_id")   # 20 min of inactivity ends a session
    .agg(F.count("*").alias("clicks"),
         F.min("click_ts").alias("first_click"), F.max("click_ts").alias("last_click")))

The gap can also be an expression, for example a shorter gap for mobile than desktop: F.session_window("click_ts", F.when(F.col("device") == "mobile", "5 minutes").otherwise("20 minutes")).

Stream-stream join with a time bound

imps = (spark.readStream.table("bronze.impressions")
             .select(F.col("ad_id").alias("imp_ad_id"), "imp_ts", "campaign")
             .withWatermark("imp_ts", "2 hours"))
clicks = (spark.readStream.table("bronze.clicks")
               .select(F.col("ad_id").alias("click_ad_id"), "click_ts")
               .withWatermark("click_ts", "3 hours"))

attributed = imps.join(clicks, F.expr("""
    click_ad_id = imp_ad_id AND
    click_ts BETWEEN imp_ts AND imp_ts + INTERVAL 1 HOUR"""), "leftOuter")

Impressions with no click within an hour come out with null click columns, but only after the click watermark passes imp_ts + 1 hour.

How much state does the join hold?

Each side is kept until the other side's watermark says no match can still arrive. Roughly: impressions stay for the click delay + time bound; clicks stay for the impression delay. Assuming event time tracks arrival time:

An estimate, not a measurement: real state also holds keys, indexes and overhead, and late or bursty data changes it. Check numRowsTotal and memoryUsedBytes in the progress metrics.

Two levers dominate: the watermark delays and the time bound. Halving the click delay here halves the impression state, which is most of the total.

Deduplication

# duplicates carry the same event time (replayed messages): include it in the key
dedup = (events.withWatermark("event_ts", "1 hour")
               .dropDuplicates(["event_id", "event_ts"]))

# retries may carry different timestamps (Spark 3.5+)
dedup = (events.withWatermark("event_ts", "1 hour")
               .dropDuplicatesWithinWatermark(["event_id"]))

Duplicates further apart than the watermark delay aren't caught. If you need a guarantee across all time, MERGE into a target keyed on event_id instead (pattern).

Keeping data the watermark drops

Spark doesn't output dropped late rows. If they matter, keep the raw stream: write Bronze without a watermark, build the windowed aggregate from it, and periodically reconcile Bronze against the aggregate (or recompute affected windows in batch). The progress metric numRowsDroppedByWatermark tells you when it's worth doing.
