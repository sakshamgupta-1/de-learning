Event time, and when to stop waiting

Aggregations, deduplication and joins across batches need state. Windows decide how events group in time; the watermark decides how long to wait for late events before a result is final and its state can be dropped. A 10-minute refresher.

Event time vs processing time

Event time is when something happened, carried in the data (event_ts). Processing time is when Spark sees it. They differ because of network delays, offline devices, retries and backfills, so events arrive out of order and late.

Grouping by event time gives correct business answers ("orders between 12:00 and 12:10") however late the data is. The cost is that Spark must keep each window's partial result in state until it decides no more events will come for it. That decision is the watermark.

Watermarks and late data

withWatermark("event_ts", "10 minutes") sets the watermark to the latest event time seen, minus 10 minutes. Events older than the watermark may be dropped; a window whose end is at or before the watermark is final, so append mode writes it and its state is deleted. Step through six micro-batches of a 10-minute tumbling count.

  • Late but within the delay (12:09 arriving after 12:14): still counted.
  • Later than the watermark (12:08 arriving when the watermark is 12:11): dropped, and counted in the progress metric numRowsDroppedByWatermark.
  • The trade-off: a longer delay accepts later data but holds more state and delays append-mode results by that much.
  • The guarantee is one-sided: data within the delay is never dropped; data beyond it may be dropped, not "will".

The state store

Each stateful operator keeps its state in a state store on the executors, split into one partition per shuffle partition and versioned per batch in the checkpoint.

Default (HDFS-backed)RocksDB

Use RocksDB for any sizeable state; Databricks recommends it, with changelog checkpointing. The provider can't be switched on an existing checkpoint without rebuilding the state.

Stream-stream joins

Both sides are unbounded, so Spark buffers each side's rows in state to match future rows from the other side. Without limits that state grows forever. Bound it with a watermark on both sides and an event-time range in the join condition:

imps   = impressions.withWatermark("imp_ts", "2 hours")
clicks = clicks_raw.withWatermark("click_ts", "3 hours")
joined = imps.join(clicks, F.expr("""
            click_ad_id = imp_ad_id AND
            click_ts BETWEEN imp_ts AND imp_ts + INTERVAL 1 hour"""), "leftOuter")
  • Inner joins: watermarks and time bounds are optional but needed to clean state; without them state grows forever.
  • Outer joins: watermarks and a time bound are required. Unmatched rows are written (with nulls) only once the watermark says no match can still arrive, so they're delayed.
  • Stream-static joins are stateless (Module 1).

Deduplication

events.withWatermark("event_ts", "1 hour").dropDuplicates(["event_id", "event_ts"])  # state bounded by the watermark
events.withWatermark("event_ts", "1 hour").dropDuplicatesWithinWatermark(["event_id"])  # Spark 3.5+

Plain dropDuplicates("event_id") on a stream keeps every id ever seen in state. Including the event-time column lets the watermark expire old keys; dropDuplicatesWithinWatermark does it when retries carry different timestamps.

Say it in an interview

Late data
"I aggregate on event time and set a watermark: the latest event time minus how late I'm willing to accept data. Anything within that delay is counted; anything older may be dropped, and the progress metrics show how many. The delay is a trade-off between completeness, state size and how soon append mode writes final results."
State
"Every stateful operator keeps state per key on the executors, checkpointed each batch. Watermarks are what let Spark delete it. For large state I use the RocksDB provider with changelog checkpointing, and I size shuffle partitions before the first run because the state is locked to that number."
Stream-stream joins
"Both sides are buffered in state, so I put a watermark on each side and an event-time range in the join condition. That's optional for inner joins but required for outer joins, and outer join nulls only appear once the watermark passes."

Quick check

Watermark delay is 10 minutes. The latest event seen is 12:30. An event for 12:25 arrives. Counted?
Yes. The watermark is 12:20, and 12:25 is newer. Even an event at 12:21 would count.
With append mode and a 10-minute tumbling window plus a 15-minute watermark, when is the 12:00–12:10 window written?
When the watermark passes 12:10, i.e. once an event with an event time of 12:25 or later has been seen, in the batch after that (or a no-data batch). So results lag event time by at least the window length plus the delay.
Two streams are unioned, each with its own watermark. Which one applies?
By default the minimum of the two (multipleWatermarkPolicy = min), so the slower stream holds back the watermark and nothing is dropped from it. max follows the faster stream and may drop the slower one's data.
Your dedup state grows every day. Why?
dropDuplicates without a watermark, or without the event-time column in the key, keeps every key forever. Add a watermark and include the event-time column, or use dropDuplicatesWithinWatermark.
Why are left-outer join results with nulls delayed?
Spark can only say "no match" once the watermark guarantees no matching row can still arrive within the join's time range. Until then the left row waits in state.
