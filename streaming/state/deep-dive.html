How state really works

Where state lives between batches, how it's checkpointed, exactly when watermarks advance and evict, how join state is cleaned up, and what to reach for when built-in operators aren't enough.

State store internals

  1. Partitioned like a shuffle. A stateful operator first shuffles rows by its key, so each key's rows and state meet in the same task. State partition n lives on whichever executor runs task n.
  2. Versioned per batch. At the end of batch N, each partition's changes are saved to state/<operator>/<partition>/ in the checkpoint as version N.
  3. Locality. Spark tries to schedule partition n on the executor that already holds it in memory. If the executor is lost, another task reloads the latest version from the checkpoint.
  4. Cleanup. Old versions beyond minBatchesToRetain are deleted by a maintenance task in the background.

RocksDB settings worth knowing

spark.conf.set("spark.sql.streaming.stateStore.providerClass",
    "org.apache.spark.sql.execution.streaming.state.RocksDBStateStoreProvider")
spark.conf.set("spark.sql.streaming.stateStore.rocksdb.changelogCheckpointing.enabled", "true")
# optional: cap memory per executor across all RocksDB instances
spark.conf.set("spark.sql.streaming.stateStore.rocksdb.boundedMemoryUsage", "true")
  • Set before the first run. The provider is recorded in the checkpoint; switching later needs a new checkpoint.
  • Changelog checkpointing uploads only the changed keys each batch and snapshots in the background, which cuts batch latency for large state.
  • Metrics: state operator progress includes RocksDB timings (commit, flush, compaction) and memory use; rising commit time is the first sign the store is struggling.
  • On Databricks, RocksDB is recommended for stateful workloads, and the same configs apply.

Watermark rules, precisely

  • Computed at the end of a batch as max event time seen − delay, and used from the next batch. It never moves backwards.
  • Late rows are filtered using the watermark in effect for the current batch.
  • Eviction: append mode writes and deletes a window when window.end <= watermark. Update mode writes changes every batch and deletes the window's state at the same point.
  • No-data batches run when the watermark has moved but no new data arrived, so results aren't held back by a quiet source. A source that goes completely quiet, though, never moves the watermark, so the last windows wait until the next event.
  • Several inputs (union, joins): each has its own watermark; the global one is their minimum by default (multipleWatermarkPolicy).
  • Complete mode ignores the watermark for cleanup, since it must output every row ever produced.
  • The watermark must be on the same column the window or event-time condition uses, and applied before the stateful operator.

How join state is cleaned up

For click_ts BETWEEN imp_ts AND imp_ts + INTERVAL 1 hour with watermarks of 2 hours on impressions and 3 hours on clicks:

  • An impression can still match clicks up to 1 hour after it. Clicks arrive up to 3 hours late. So Spark keeps an impression until the click watermark passes imp_ts + 1 hour.
  • A click can match impressions up to 1 hour before it, which arrive up to 2 hours late. So it's kept until the impression watermark passes click_ts.
  • For a left outer join, the impression's null row is written when it's evicted without a match, which is why outer join results are delayed by the watermark delay plus the time bound.

InnerOptional; needed to clean up state

Arbitrary stateful processing

When windows, aggregations and joins don't express the logic (custom sessionisation, alerts on sequences, per-key state machines), use an API that hands you state per key:

APILanguageNotes
mapGroupsWithState / flatMapGroupsWithStateScala, JavaOne state object per key, optional timeouts
applyInPandasWithState (Spark 3.4+)Pythonpandas DataFrames per key, one state per key, timeouts
transformWithState (Spark 4.0+)Scala, Java; transformWithStateInPandas for PythonSeveral typed state variables (value, list, map) per key, timers, state TTL, schema evolution

Always give state a lifetime: a timeout, a TTL, or explicit removal. State without one grows forever, just like a stream-stream join without watermarks.

Inspecting state

  • Progress metrics per stateful operator: numRowsTotal, numRowsUpdated, numRowsRemoved, memoryUsedBytes, numRowsDroppedByWatermark.
  • State data source (Spark 4.0+, and on recent Databricks runtimes): read a checkpoint's state as a table to debug it, e.g. spark.read.format("statestore").load("/chk/q1"), and format("state-metadata") for the operators.
  • SQL tab: the stateful operator node shows rows in state and time spent committing state per batch.

Check yourself

The last hour of windows is never written on Sunday nights, when traffic stops. Why?
The watermark only moves when new events arrive. With no events, it stays where it was, so the last windows never pass it until Monday's first events. Options: accept the delay, send heartbeat events, or use update mode so partial results are visible.
Why can't you add RocksDB to an existing query by just changing the config?
The provider is part of the checkpoint metadata, and the state files are in the old provider's format. Switching needs a new checkpoint, which means rebuilding state (reprocessing enough history) or accepting a fresh start.
A custom applyInPandasWithState job's state grows forever. Where do you look first?
Whether state is ever removed: a timeout configured and handled (calling state.remove() when it fires), or keys removed when their logic completes.
