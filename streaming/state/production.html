When state goes wrong

Stateful streams fail slowly: state creeps up for weeks, or data disappears without an error. Each issue follows symptom → why → confirm → fix → prevent → interview answer.

State that never stops growing

Symptom

Batch duration and executor memory rise week after week with flat input volume, until executors fail.

Why it happens

Something keeps state without a way to expire it: an aggregation or dropDuplicates without a watermark, a stream-stream join without watermarks and a time bound, the watermark on a different column than the window, or custom state without timeouts.

How to confirm

  1. stateOperators[].numRowsTotal in the progress metrics only goes up; numRowsRemoved stays at 0.
  2. Check each stateful operator for a watermark on the column it groups or joins by.

Fix

  • Add the missing watermark (and event-time column in dedup keys, or a time range in joins), or timeouts for custom state.
  • Adding a watermark changes the state's meaning: plan a new checkpoint and a state rebuild (replay).

Prevent

  • Review rule: every stateful operator needs a stated lifetime. Alert on state rows growing faster than input.
Say it in an interview
"Unbounded state almost always means a stateful operator without a watermark, or a join without a time bound. I confirm it from numRowsTotal never decreasing, then add the watermark, which usually means a new checkpoint."

Data silently dropped as late

Symptom

Streaming aggregates are lower than a batch recount of the same period, especially after an upstream outage or a device fleet coming back online.

Why it happens

After a delay, events arrive older than the watermark and are dropped. The watermark is driven by the newest event, so one source or partition running ahead can push it past data others haven't delivered yet.

How to confirm

  1. numRowsDroppedByWatermark is non-zero around the gap.
  2. Compare event time with ingestion time in Bronze for the missing rows.

Fix

  • Recompute the affected windows in batch from Bronze and overwrite them.
  • Increase the delay if regular lateness exceeds it; use update mode with MERGE so late rows correct results instead of being dropped.

Prevent

  • Set the delay from the measured lateness distribution (for example its 99.9th percentile), keep raw Bronze, and alert on dropped rows.
Say it in an interview
"The watermark drops rows silently, so I monitor numRowsDroppedByWatermark, size the delay from measured lateness, and keep raw Bronze so I can recompute windows after an outage."

Executor memory pressure from state

Symptom

Long GC pauses and executor OOMs in the stateful stage; restarts take minutes as state reloads.

Why it happens

The default provider keeps state as JVM objects on the heap, plus cached versions. Millions of keys per executor overwhelm the heap.

How to confirm

  1. memoryUsedBytes per operator is a large share of executor memory.
  2. GC time in the stateful stage is high (GC signals).

Fix

  • Move to the RocksDB provider with changelog checkpointing (needs a new checkpoint).
  • Reduce state: shorter watermark, fewer or narrower columns in state.
  • More memory per executor, or more executors so partitions spread out.

Prevent

  • Estimate state size before launch (calculator) and start sizeable stateful queries on RocksDB.
Say it in an interview
"The default state store lives on the heap, so large state means GC pauses and OOMs. I use RocksDB with changelog checkpointing for anything sizeable, and keep state lean with tight watermarks."

Slow state commits

Symptom

Batches take much longer than the processing itself; the duration breakdown shows time going to commit or state maintenance.

Why it happens

Every batch uploads state changes to the checkpoint. With large state, uploading full RocksDB files, or many small delta files on slow storage, dominates.

How to confirm

  1. stateOperators[].commitTimeMs in the progress metrics, and the RocksDB commit timings, grow with state size.

Fix

  • Enable changelog checkpointing.
  • Use a longer trigger interval so commits happen less often.
  • Check state partition count: too many tiny partitions multiply per-partition overhead.

Prevent

  • Choose shuffle partitions for a stateful query deliberately before its first run; it's fixed afterwards.
Say it in an interview
"When commit time dominates, it's state checkpointing. Changelog checkpointing on RocksDB uploads only the changes; I also check the trigger interval and the state partition count, which is fixed at the first run."

A query change breaks the checkpoint

Symptom

After a code change, the query fails on start with a state schema incompatibility or "the number of stateful operators changed" style error.

Why it happens

State is stored in the schema of the original grouping keys and aggregates. Changing keys, aggregations, join type, the number of stateful operators or their order makes the old state unreadable.

How to confirm

  1. The error names the operator and the old and new state schema.
  2. Diff the stateful part of the query against the last deployed version.

Fix

  • Revert, or start a new checkpoint and rebuild state by reprocessing enough history (replay playbook).

Prevent

  • Treat stateful logic changes as migrations: plan the new checkpoint and backfill. Stateless changes (filters, projections) are usually safe.
Say it in an interview
"State is stored in the shape of the original query, so changing keys or aggregations needs a new checkpoint. I plan those as migrations with a backfill, whereas filters and projections can change in place."

Results that never appear

Symptom

An append-mode windowed table stops getting new rows, though the source still has recent data, or the last windows of the day never arrive.

Why it happens

  • The watermark only advances with new events; a quiet source holds it still.
  • With several inputs, the minimum watermark follows the slowest one; an idle Kafka partition or a dead upstream holds everything back.

How to confirm

  1. The eventTime.watermark in progress hasn't moved for hours.
  2. Check per-input event times for one stuck behind the rest.

Fix

  • Fix or remove the idle input; consider multipleWatermarkPolicy=max only if dropping the slow input's late data is acceptable.
  • Send heartbeat events, or use update mode so partial results are visible.

Prevent

  • Alert on watermark lag (now − watermark) as well as batch freshness.
Say it in an interview
"Append mode waits for the watermark, and the watermark only moves with new events from every input. I alert on watermark lag so a quiet or stuck input shows up before users notice missing results."
