When ingestion breaks

Six failures at the edges of a stream: discovering files, schema drift, Kafka retention, bad messages, MERGE targets and upstream rewrites. Each follows symptom → why → confirm → fix → prevent → interview answer.

Slow file discovery

Symptom

Batches spend most of their time before any task runs; runtime grows month by month with flat daily volume.

Why it happens

Directory listing examines every file in the folder each batch, so its cost tracks the folder's total size.

How to confirm

  1. A long gap before the first job of each batch in the Spark UI (driver-side listing).
  2. durationMs.latestOffset / getBatch in the progress metrics is large and growing.

Fix

  • Switch to file notifications or managed file events. The discovery mode can change across restarts while keeping the checkpoint.
  • Move processed files out of the landing folder once they're safely ingested (a storage lifecycle rule after a retention period).

Prevent

  • Choose discovery mode from the expected folder size; date-partition landing paths.
Say it in an interview
"Listing cost grows with the whole folder, so a stream that slows down while volume is flat is usually discovery. I move it to file notifications or managed file events and archive processed files."

A schema change stops the stream

Symptom

The Bronze stream fails with UnknownFieldException after a source adds a column; or, worse, keeps running while a type change sends values to _rescued_data.

Why it happens

With addNewColumns, Auto Loader fails once on purpose so the schema can be updated; a job without retries stays failed. Type changes don't evolve the schema; mismatching values are rescued.

How to confirm

  1. The exception names the new fields; the schema location has a new version.
  2. Rescued rows: SELECT count(*) FROM bronze.x WHERE _rescued_data IS NOT NULL by day.

Fix

  • Restart (or let retries restart) to pick up new columns; make sure the sink allows schema evolution (mergeSchema).
  • For type changes: update schema hints, reprocess affected files, and fix downstream casts.

Prevent

  • Run with retries; alert on rescued data; agree schema change rules with the source team (a data contract).
Say it in an interview
"Auto Loader's default evolution mode fails once on a new column and continues after a restart, so I always run it with retries. Type changes don't evolve; they land in rescued data, which I monitor as a drift signal."

Kafka data loss

Symptom

The query fails with "Some data may have been lost because they are not available in Kafka any more", typically after an outage or a long pause.

Why it happens

The topic's retention deleted messages before the stream read them: the next offset in the checkpoint is older than the earliest offset still in Kafka.

How to confirm

  1. Compare the checkpoint's last offsets with the partition's earliest offset.
  2. Check the outage length against retention.ms.

Fix

  • Recover the missing range from another copy (a mirror, an archive, the source system).
  • If it's truly gone, restart deliberately past the gap and record it; failOnDataLoss=false only for streams where gaps are acceptable.

Prevent

  • Retention comfortably longer than the worst recovery time; alert on consumer lag in time ("minutes behind"), not just records.
Say it in an interview
"That error means retention outran the consumer. Spark fails by default rather than silently skipping, which is right. I recover the range from another copy if I can, and prevent it with retention sized to recovery time and lag alerts."

Undecodable messages

Symptom

One bad message fails every batch from that point (a crash loop), or decoded rows are suddenly all null.

Why it happens

A producer wrote with an unregistered or incompatible schema, plain JSON on an Avro topic, or a corrupted payload. from_avro fails in its default FAILFAST mode; in PERMISSIVE mode it returns nulls.

How to confirm

  1. Read the failing offset range in batch and inspect the first bytes (magic byte, schema id).
  2. Check the registry for the schema id found.

Fix

  • Decode permissively and route rows that fail to decode to a quarantine table, with topic, partition and offset.
  • Fix the producer; replay quarantined messages once decodable.

Prevent

  • Enforce schemas at the producer (registry-aware serialisers, compatibility checks in CI); alert on quarantine volume.
Say it in an interview
"I never let one bad message stop a pipeline: I decode permissively, quarantine failures with their offsets, and alert on that table. The real fix is schema enforcement at the producer."

MERGE failures in foreachBatch

Symptom

Batches fail with "multiple source rows matched", or with ConcurrentAppendException / ConcurrentDeleteReadException; or the MERGE gets slower every week.

Why it happens

  • Several changes for one key in a batch.
  • Another job writes the same table, or files the MERGE read were rewritten (OPTIMIZE, another MERGE) during the batch.
  • The MERGE condition can't prune the target, so every batch scans the whole table.

How to confirm

  1. The exception type; the table history (DESCRIBE HISTORY) around the failure.
  2. MERGE metrics: target files scanned vs rewritten.

Fix

  • Deduplicate the batch to one row per key.
  • Avoid concurrent writers on the same files: partition or cluster so they touch disjoint data, schedule OPTIMIZE apart, rely on retries (the batch is replayed safely if the MERGE is idempotent).
  • Add a pruning predicate (date or cluster key) to the MERGE condition; enable deletion vectors.

Prevent

  • Treat every streaming MERGE as replayable and concurrent: dedupe, version guard, pruning predicate.
Say it in an interview
"Streaming MERGE needs one row per key per batch, a version guard so replays are harmless, and a predicate that prunes the target. Concurrency conflicts get retried, which is safe because the MERGE is idempotent."

An upstream rewrite breaks a Delta source

Symptom

A Silver stream reading Bronze fails with an error saying the source table had an update or delete, right after a backfill, GDPR delete or MERGE on Bronze.

Why it happens

The Delta streaming source only supports appends; a commit that changes existing rows can't be expressed as new rows.

How to confirm

  1. DESCRIBE HISTORY bronze.x shows a DELETE, UPDATE or MERGE at the failing version.

Fix

  • Restart with skipChangeCommits=true and apply the correction downstream separately.
  • If downstream must follow upstream changes, stream the change feed and MERGE it instead (example).

Prevent

  • Keep Bronze append-only; route corrections through new rows, and plan GDPR deletes across layers.
Say it in an interview
"A Delta stream source is append-only. When upstream rewrites rows, I either skip change commits and handle the correction downstream, or switch to the change feed with a MERGE so updates and deletes propagate."
