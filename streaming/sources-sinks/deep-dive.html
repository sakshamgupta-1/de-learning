Auto Loader internals

  • File tracking: discovered files are recorded in a RocksDB key-value store under the checkpoint's sources/ folder. A file path is processed once, even if it's listed or notified again. A file overwritten in place at the same path isn't re-ingested unless cloudFiles.allowOverwrites is set.
  • First run: includeExistingFiles=true (default) ingests what's already there; modifiedAfter / modifiedBefore limit by file time.
  • Batch size: maxFilesPerTrigger (1,000) and maxBytesPerTrigger; a file is never split across micro-batches.
  • Notification mode safety net: cloudFiles.backfillInterval (for example "1 day") runs an asynchronous listing to catch files whose events were lost.
  • Moving checkpoints: the RocksDB file list is tied to the checkpoint; a new checkpoint means Auto Loader rediscovers everything (limit it with modifiedAfter).
  • How micro-batches turn into Spark jobs and tasks for Auto Loader: Spark Core case study.

Schema inference and evolution

With cloudFiles.schemaLocation set, Auto Loader samples files (up to 50 GB or 1,000 files by default) to infer a schema and stores it under that location, versioned. For JSON, CSV and XML, columns are inferred as strings unless cloudFiles.inferColumnTypes=true; use cloudFiles.schemaHints to pin types you know.

schemaEvolutionModeWhen a new column appears
addNewColumns (default without a given schema)The stream fails once with an UnknownFieldException; the stored schema gains the column; the restart continues with it. Existing column types never change.
rescueSchema never changes; new columns' data goes into _rescued_data. The stream keeps running.
failOnNewColumnsThe stream fails and stays failed until someone updates the schema or removes the file.
none (default with a given schema)New columns are ignored; nothing is rescued unless rescuedDataColumn is set.

_rescued_data also catches values that don't match the column type and fields whose name differs only by case, as JSON, so nothing is silently lost. Monitor it: rows with rescued data mean the source is drifting.

Run jobs with retries so addNewColumns restarts are automatic. Lakeflow pipelines restart on schema change for you.

Kafka offsets and rate controls

  • New partitions added to a topic are picked up automatically, from their earliest offset.
  • Subscribe options: subscribe (list), subscribePattern (regex), assign (specific partitions). Changing which topics a query reads is one of the changes that usually needs a new checkpoint.
  • Ordering is per partition only; there's no global order across a topic.

The Avro wire format and compatibility rules

byte 0      magic byte (0)
bytes 1–4   schema id in the registry (big-endian int)
bytes 5…    Avro binary, written with that schema (no schema inside)

Avro resolves a writer's schema against a reader's schema field by name: fields in the writer but not the reader are skipped; fields in the reader but not the writer take the reader's default, or fail if there's none. Compatibility modes are just this rule applied in one or both directions:

ChangeBACKWARDFORWARDFULL
Add field with defaultyesyesyes
Add field without defaultnoyesno
Remove field with defaultyesyesyes
Remove field without defaultyesnono
Widen int → longyesnono
Rename, or string ↔ intnonono
  • Spark is a consumer with a fixed schema per query unless you resolve schemas per message. With open-source from_avro, pass the latest reader schema; under BACKWARD compatibility it can read all earlier messages.
  • Subjects are usually <topic>-value and <topic>-key (TopicNameStrategy).
  • Protobuf and JSON Schema use the same registry and wire-format idea with their own compatibility rules.

Delta tables as a streaming source

  • A Delta source reads new commits: startingVersion / startingTimestamp for a new checkpoint, then each batch's new data files, up to maxFilesPerTrigger (1,000) or maxBytesPerTrigger.
  • It expects an append-only table. A commit that changes existing rows (UPDATE, DELETE, MERGE) makes the stream fail, unless you tell it how to treat such commits. OPTIMIZE is fine: its commits are marked as not changing data.
OptionBehaviour
skipChangeCommitsSkip commits that change existing rows; only appends flow. Recommended when downstream should ignore upstream corrections
ignoreDeletesIgnore commits that only delete whole partitions
ignoreChanges (deprecated)Re-emit every row of rewritten files, producing duplicates
readChangeFeedStream the Change Data Feed instead: inserts, updates (pre and post images) and deletes, with _change_type

To propagate updates and deletes downstream, stream the change feed and MERGE it, or use AUTO CDC in a Lakeflow pipeline.

Check yourself

A vendor re-sends a corrected file with the same name. Auto Loader ignores it. Why, and what are the options?
Auto Loader tracks files by path and treats an overwritten path as already ingested. Ask for new file names on corrections, or set cloudFiles.allowOverwrites=true and make the downstream write idempotent (MERGE on a key), since the whole file is ingested again.
All your Auto Loader JSON columns are strings. Bug?
No: type inference is off by default for JSON and CSV. Set cloudFiles.inferColumnTypes=true or provide schema hints, ideally before the first run so the stored schema starts correct.
A Silver stream reading a Bronze Delta table fails after someone ran a GDPR DELETE on Bronze. Fix?
The Delta source saw a commit that rewrote files. Restart with skipChangeCommits=true so such commits are skipped, and apply the same deletion to Silver separately (or propagate it via the change feed).
