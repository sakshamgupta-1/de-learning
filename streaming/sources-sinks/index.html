Getting data in, and out exactly once

Most production streams read files with Auto Loader or events from Kafka, and write to Delta, often through foreachBatch and MERGE. Each has its own way of tracking progress, handling schema change and staying exactly-once. A 10-minute refresher.

Auto Loader: files in cloud storage

Auto Loader (format("cloudFiles"), Databricks) incrementally ingests new files from a folder. It records every file it has discovered in a RocksDB store inside the checkpoint, so each file is processed exactly once, even across restarts. The main design choice is how it discovers new files:

Schema handling: give Auto Loader a cloudFiles.schemaLocation and it infers the schema, stores it, and evolves it. By default (addNewColumns) a new column stops the stream once; the restart picks it up. Values that don't fit the schema go to _rescued_data instead of being lost.

Kafka source: offsets live in the checkpoint

  • Parallelism: by default one Spark task per Kafka partition per batch. minPartitions splits large partitions across more tasks.
  • Progress: Spark stores the offsets it processed in the checkpoint, not in Kafka. It doesn't commit offsets to a consumer group, so consumer-group lag tools don't show its lag unless you report it yourself; the progress metrics include offsets behind latest.
  • Consumer group: generated per query by default. Setting kafka.group.id is mainly for ACLs or quotas; two queries must not share one.
  • Start: startingOffsets applies only to a new checkpoint. Its default for streams is latest; use earliest or explicit JSON offsets to backfill.
  • Data loss: if retention deletes offsets the stream hasn't read yet, the query fails (failOnDataLoss=true). Setting it to false lets the stream continue, but the data is gone.

Kafka with Avro and a schema registry

Producers serialise each message with an Avro schema registered in a schema registry; the message carries the schema id (Confluent wire format: one magic byte plus a 4-byte id, then the Avro bytes). Consumers fetch the schema by id. The registry enforces a compatibility mode per subject, which decides which schema changes are allowed and who must upgrade first. Try a change:

ModeGuaranteeUpgrade first
BACKWARDConsumers on the new schema can read data written with the previous oneConsumers
FORWARDConsumers on the previous schema can read data written with the new oneProducers

*_TRANSITIVEAgainst all earlier versions, not just the previous oneAs above

Decoding in Spark: open-source from_avro takes a fixed schema, so you strip the 5-byte header and pass the JSON schema; Databricks' from_avro can look schemas up in the registry directly. Code: examples.

foreachBatch + MERGE: streaming upserts

The Delta sink can only append or overwrite. To apply updates and deletes (CDC, latest state per key), MERGE each micro-batch into the target:

from delta.tables import DeltaTable
from pyspark.sql import Window, functions as F

def upsert(batch, batch_id):
    latest = (batch.withColumn("rn", F.row_number().over(
                  Window.partitionBy("customer_id").orderBy(F.desc("updated_at"))))
                   .where("rn = 1").drop("rn"))                     # one row per key per batch
    (DeltaTable.forName(spark, "silver.customers").alias("t")
        .merge(latest.alias("s"), "t.customer_id = s.customer_id")
        .whenMatchedUpdateAll(condition="s.updated_at > t.updated_at")  # ignore stale updates
        .whenNotMatchedInsertAll()
        .execute())

(spark.readStream.table("bronze.customers_cdc")
      .writeStream.foreachBatch(upsert)
      .option("checkpointLocation", "/chk/silver_customers").start())
  • Deduplicate within the batch first: MERGE fails if several source rows match one target row.
  • Order guard (updated_at > t.updated_at) makes replays and out-of-order batches harmless, so the MERGE is idempotent.
  • In Lakeflow pipelines, AUTO CDC (APPLY CHANGES) does this, including SCD Type 2.

Say it in an interview

Auto Loader
"Auto Loader tracks every discovered file in RocksDB inside the checkpoint, so files are ingested exactly once. Directory listing is simple but its cost grows with the folder; for large or busy folders I use file notifications or managed file events, so discovery scales with new files only. I give it a schema location so it infers and evolves the schema, with a rescued-data column for anything that doesn't fit."
Kafka
"Spark reads one task per Kafka partition and stores offsets in its checkpoint, not in a consumer group. The source is replayable, so with a Delta sink it's exactly-once end to end. Writing back to Kafka is at-least-once, so downstream consumers need a key to dedupe on."
Schema registry
"Messages carry a schema id and the registry enforces compatibility. Under BACKWARD, the default, I can add fields with defaults or remove fields, and consumers upgrade first; under FORWARD producers upgrade first. Renames and type changes are breaking, so they go to a new field or a new topic."

Quick check

Directory listing has worked for a year, and now discovery takes longer than processing. Why?
Listing cost grows with the number of files in the folder, not with the new ones. Switch to file notifications or managed file events, or use a date-partitioned path layout so listing covers less.
You restart a Kafka stream with startingOffsets="earliest" to reprocess. Nothing is reprocessed. Why?
startingOffsets only applies to a new checkpoint; with an existing one, the query resumes from its stored offsets. Reprocessing needs a new checkpoint.
The query fails with "Some data may have been lost because they are not available in Kafka any more". Options?
Retention deleted offsets before Spark read them. Restore the data from another copy if possible; otherwise, deliberately accept the gap (failOnDataLoss=false or new offsets) and record it. Prevent it with retention well above the longest expected outage, and alerts on lag.
Under BACKWARD compatibility, a producer adds a field without a default. What happens?
The registry rejects the new schema: consumers on the new schema couldn't read old messages, which lack the field. Add a default.
Your MERGE in foreachBatch fails with "multiple source rows matched". Fix?
The batch has several changes for the same key. Keep only the latest per key (window with row_number) before merging.
