Who does what in a Spark application

Every tuning answer you give later depends on this picture: one driver that plans, many executors that do the work, and a cluster manager that hands out machines.

ComponentsVocabularyJobs, stages, tasksDeploy modesMemory modelDynamic allocationCheck yourself

The three moving parts

A Spark application is one driver process plus the executors it gets from the cluster manager. The driver never processes your data rows in a healthy job. It plans and coordinates; executors read, transform, shuffle and write.

  1. The driver asks the cluster manager for executors (fixed count, or dynamic allocation).
  2. The cluster manager starts executor JVMs on worker nodes with the requested cores and memory.
  3. Executors register back with the driver. From now on the driver talks to them directly.
  4. For each stage, the task scheduler sends tasks (your serialised code plus one partition to work on) to free cores, preferring executors that already hold that data.
  5. Executors report status and send small results back. Shuffle files and cached data stay on the executors.
Say it in an interview
"The driver builds the plan and schedules tasks; executors are JVMs on worker nodes that run those tasks in parallel, one per core, and hold shuffle files and cached data. The cluster manager only allocates resources; it does not schedule tasks."

A useful mental model: total slots is how many tasks run at once. If a stage has 400 tasks and you have 100 slots, it runs in about four "waves".

Executor memory, slice by slice

Most OOM and spill questions come back to this layout. Since Spark 1.6 the heap uses unified memory: execution memory (shuffles, joins, sorts, aggregations) and storage memory (cache, broadcast) share one pool and can borrow from each other.

Defaults used: 300 MB reserved, spark.memory.fraction = 0.6, spark.memory.storageFraction = 0.5, overhead = max(384 MB, factor × heap).

How the pool behaves under pressure

  • Execution can evict storage. If a join needs memory, cached blocks are dropped back down to the protected storage share (storageFraction).
  • Storage cannot evict execution. Cache can only use execution memory that is free.
  • When execution memory runs out, sorts and aggregations spill to local disk. That is slow but survives. Running out of heap for objects that cannot spill causes OutOfMemoryError.
  • Memory per task ≈ execution pool ÷ cores. More cores per executor means less memory per running task. This is why reducing cores (not adding memory) sometimes fixes spill.
  • Overhead sits outside the heap: JVM internals, network buffers, and Python worker processes for PySpark UDFs. "Container killed for exceeding memory limits" is an overhead problem, not a heap one.

Dynamic allocation and speculation

Dynamic allocation

Spark adds executors when tasks are queued and removes them when they sit idle. Good for shared clusters and spiky workloads.

spark.dynamicAllocation.enabled=true
spark.dynamicAllocation.minExecutors=2
spark.dynamicAllocation.maxExecutors=50
spark.dynamicAllocation.executorIdleTimeout=60s
# executors hold shuffle files, so removal needs one of:
spark.dynamicAllocation.shuffleTracking.enabled=true   # or an external shuffle service

Speculative execution

spark.speculation=true launches a duplicate copy of a task that runs much slower than its siblings, and keeps whichever finishes first. It helps with a bad node or a noisy neighbour.

Common trap
Speculation does not fix data skew. A skewed task is slow because it has more data, so its duplicate is just as slow and wastes a core. Fix skew in the data or with AQE (Module 4).

Check yourself

Does the cluster manager schedule tasks?
No. It only allocates containers or pods for executors. Task scheduling is done by the driver's DAG scheduler and task scheduler.
You have 10 executors with 4 cores each. A stage has 1,000 tasks. Roughly how does it run?

Each core is a slot that runs one task at a time, so 10 × 4 = 40 tasks run at once. The other tasks wait and start as slots free up. 1,000 ÷ 40 = 25 rounds, called waves. Think of 40 checkout counters serving 1,000 customers.

If each task takes about 20 s: 25 waves × 20 s ≈ 500 s, roughly 8–9 minutes. In practice slots pick up the next task as soon as they finish, so the waves blur together, but the total is the same.

What actually makes it faster:

  • More slots (executors or cores). 80 slots → about 13 waves → roughly half the time. This is the main lever.
  • No half-empty last wave. 1,010 tasks need 26 waves, and the last runs only 10 tasks while 30 cores sit idle. Keep task counts near a multiple of total cores.
  • Merging only tiny tasks. Fewer, larger partitions do not speed this stage up: total work is the same, each task just runs longer. It only helps when tasks take ~100 ms and scheduling overhead dominates.
  • Fixing skew. A stage ends when its slowest task ends. One 15-minute task makes the stage take at least 15 minutes, however many slots you add.

Say it: "40 slots means 25 waves of 20 s, about 8 minutes. To speed it up I'd add slots, keep the task count a multiple of the cores, and check the max task time, because one skewed task sets the floor."

A 16 GB executor with 4 cores spills heavily. Name two fixes that don't add memory.
Use more shuffle partitions so each task handles less data, or reduce cores per executor to 2 so each task gets roughly twice the execution memory. Also check for skew, since one huge partition spills regardless.
"Container killed by YARN for exceeding memory limits." Heap or overhead?
Overhead. The process as a whole (heap + off-heap + Python workers) exceeded the container limit. Raise spark.executor.memoryOverhead, reduce Python UDF memory use, or lower cores per executor.
Why should the driver not be doing heavy work?
It is one JVM. Pulling data to it (collect, toPandas) or building huge broadcasts there creates a single-machine bottleneck and the most common driver OOM.
