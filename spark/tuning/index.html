Finding and fixing slow Spark jobs

Interviewers rarely ask "what is skew?" on its own. They describe a slow or failing job and watch how you investigate. Learn the debug flow, the levers in priority order, and the defaults behind them. A 10-minute refresher.

Evidence first, settings last

Tuning is finding the one stage that dominates the runtime, working out why from its metrics, and applying the smallest fix for that cause. Changing memory or partition settings before you know the cause usually moves the problem somewhere else.

Almost every slow or failing job comes down to five causes: out of memory, skew, spill, too many small files or tasks, and too much shuffle. The Spark UI tells you which one, and each has a standard set of fixes.

The debug flow

Start in the Spark UI: Jobs → the slowest job → Stages → the slowest stage → its summary metrics (min, 25th percentile, median, 75th percentile and max per task). Answer each question below for that stage; a "yes" leads to the scenario to read. You can also click any outcome directly.

The levers, in priority order

Once you know the cause, reach for the cheapest lever that addresses it. Higher in the list usually means a bigger gain for less risk.

LeverFixesHow
Read lessSlow scans, heavy shuffleEarly filters and projections, partition pruning, compaction
Shuffle lessHeavy shuffle, slow joinsBroadcast small sides, pre-aggregate, remove accidental shuffles
Balance the workSkew, stragglersAQE skew join, handle NULL keys, salting
Right-size partitionsSpill, OOM, tiny tasksAbout 100–200 MB per shuffle partition; AQE coalescing
Memory per taskOOM, spillFewer cores per executor, more memory or overhead
Cache reused resultsRepeated recomputationpersist() on classic compute; an intermediate table elsewhere
Cluster size and shapeEverything is evenly slowMore or larger workers, autoscaling, instance type

The details behind each lever: reducing shuffle, repartition vs coalesce, cache vs persist, partition sizing and executor sizing.

Say it in an interview

How you debug
"I start in the Spark UI: find the slowest job and stage, then read that stage's summary metrics. Max versus median task time tells me if it's skew; spill columns tell me partitions are too big for the memory per task; failed tasks and their errors tell me if it's an OOM; task and file counts reveal small files; and the SQL tab shows the join strategy and how much is shuffled. Then I fix that specific cause."
What you change first
"I fix the data flow before the cluster: read less, shuffle less, balance skew, then right-size partitions. Executor memory and cluster size come last, because they cost money and often just hide the cause."
Skew in one breath
"One key holds most of the rows, so one task does most of the work. I confirm it from max versus median shuffle read, check for NULL keys, then use AQE skew joins, a broadcast, or salting with a two-step aggregation."

Quick check

"Our nightly job went from 1 hour to 4 hours. Nothing changed in the code." Where do you start?
Compare with a previous good run and find which stage grew. Then check input volume (did a filter stop pruning?), task-time distribution (a new hot key), spill (data outgrew memory per task), file counts, and whether a dimension crossed the broadcast threshold. Full walkthrough: production issues.
199 tasks finish in 30 s, one takes 45 min. Name three fixes.
AQE skew-join handling (for a sort-merge join), broadcast the smaller side, or salt the hot key. First check whether the hot key is NULL or a default value.
When would you increase spark.sql.shuffle.partitions, and when decrease it?
Increase when post-shuffle partitions are large (spill, OOM, long tasks); decrease when they're tiny (many short tasks, small output files). With AQE, set it high and let coalescing reduce it.
Heap is fine, but containers are killed with exit code 137. What do you change?
The process exceeded its container limit outside the heap, often Python workers or native memory. Raise spark.executor.memoryOverhead, reduce Python UDF memory, or prefer built-in functions.
coalesce or repartition to write fewer files after a heavy aggregation?
Usually repartition: coalesce shrinks the parallelism of the whole stage it's in, so the aggregation itself runs on few tasks. See the trap.
