Six ways Spark jobs fail or crawl

The scenarios the debug flow leads to. Each one: what you see, why it happens, how to confirm it, how to fix it, how to prevent it, and a short interview answer. Metrics are representative examples, not benchmarks.

Data skew

Symptom

One or a few tasks run far longer than the rest; the stage sits at 199/200 for most of its runtime.

Metric (example)Min25thMedian75thMax
Duration2 s3 s4 s5 s38 min
Shuffle read60 MB75 MB80 MB90 MB9.6 GB
Spill (disk)000014 GB

Why it happens

Rows are hashed to shuffle partitions by key. If one key (a big customer, a default value, NULL) holds a large share of the rows, all of them land in one partition and one task. That task can also spill or run out of memory, because only its own share of executor memory is available.

How to confirm

  1. In the slow stage, compare max with median for Duration and Shuffle Read Size. The Event Timeline shows one long bar.
  2. Find the join or groupBy key for that stage in the SQL tab.
  3. Count rows per key to find the hot keys:
df.groupBy("cust_id").count().orderBy(F.desc("count")).show(10)

Fix

  • Handle NULL or default keys separately. It's the most common hidden cause: filter them out, or join them on their own.
  • Let AQE split it (sort-merge joins only): keep spark.sql.adaptive.skewJoin.enabled=true. A partition counts as skewed when it's over 5 × the median and over 256 MB.
  • Broadcast the smaller side, so the large side isn't shuffled by the key at all.
  • Salt the hot key for joins AQE can't split and for skewed aggregations. Step-by-step with an animation: salting example.
N = 16
big   = orders.withColumn("salt", (F.rand() * N).cast("int"))
small = customers.withColumn("salt", F.explode(F.array([F.lit(i) for i in range(N)])))
joined = big.join(small, ["cust_id", "salt"]).drop("salt")

Prevent

  • Profile key distributions when onboarding a source; track the top keys' share over time. Keep AQE on, and treat NULL join keys as a data-quality rule.
Say it in an interview
"I confirm skew by comparing max and median task time and shuffle read in the stage metrics, then count rows per key to find the hot keys. First I check for NULL or default keys; then I rely on AQE's skew-join handling or broadcast the smaller side. For skewed aggregations, or when AQE can't help, I salt the key and aggregate in two steps."

Executor OOM

Symptom

Tasks fail with java.lang.OutOfMemoryError: Java heap space, or the container is killed (YARN: "exceeding memory limits"; Kubernetes: OOMKilled, exit code 137). Executors disappear and stages retry.

Metric (example)Min25thMedian75thMax
Duration40 s52 s1.1 min1.3 minfailed ×4
Shuffle read700 MB820 MB900 MB1.1 GB3.8 GB
GC time2 s3 s4 s9 s6 min

Why it happens

Something needs more memory than one task gets: very large partitions, a skewed key, groupByKey or collect_list building huge lists, exploding arrays, a large broadcast, or Python worker memory outside the JVM heap. How memory is split per task is in Module 1.

How to confirm

  1. Read the exact error. "Java heap space" or "GC overhead limit exceeded" = heap. "Container killed … memoryOverhead" or exit code 137 = off-heap, native or Python memory.
  2. Check whether only a few tasks fail (skew) or all of them (partitions too big for the memory per task).
  3. Check GC time: high GC before the failure confirms heap pressure.
  4. Check the SQL tab for row counts that explode after a join or explode.

Fix

  • Smaller partitions: raise spark.sql.shuffle.partitions, or repartition before the heavy step.
  • Fix skew if only some tasks fail.
  • More memory per task: fewer cores per executor, or more executor memory.
  • Heap fine but container killed: raise spark.executor.memoryOverhead; cut Python UDF memory; prefer built-ins or pandas UDFs.
  • Replace groupByKey / collect_list on unbounded groups with real aggregations.
spark.conf.set("spark.sql.shuffle.partitions", 800)
# cluster-level, set at launch:
# spark.executor.memory=24g
# spark.executor.memoryOverhead=4g
# spark.executor.cores=4

Prevent

  • Alert on task retries and lost executors, not just job failure. Load-test with production-sized data, and review any code that collects values into lists per key.
Say it in an interview
"First I read the error to tell heap OOM from container-killed, which points to overhead or Python memory. Then I check whether all tasks fail or only a few: a few means skew, all means partitions are too big for the memory per task. The fixes are more, smaller partitions; fewer cores per executor or more memory; more overhead for PySpark; and fixing skew."

Driver OOM

Symptom

The application dies with an OutOfMemoryError on the driver, or "Total size of serialized results … is bigger than spark.driver.maxResultSize". Executors were healthy.

Why it happens

The driver is one JVM. It runs out when data is pulled to it (collect(), toPandas(), take() with a big n), when a large table is broadcast (the driver collects it to build the broadcast), when it lists hundreds of thousands of files, or when a long-running app keeps many large plans and UI state.

How to confirm

  1. Find the last action before the crash in the driver log.
  2. Look for collect, toPandas or a broadcast() on large data.
  3. Check how many files and partitions the job reads (listing pressure).

Fix

  • Write results to a table instead of collecting; use limit() for samples.
  • Lower autoBroadcastJoinThreshold, or remove a broadcast hint on a big table.
  • Compact small files so fewer are listed.
  • Only if the driver genuinely needs more: spark.driver.memory, spark.driver.maxResultSize (default 1g).
# instead of
pdf = big_df.toPandas()
# do
big_df.write.mode("overwrite").saveAsTable("tmp.result")
sample = big_df.limit(1000).toPandas()

Prevent

  • Code review rule: no unbounded collect or toPandas in pipelines. More on toPandas in Module 2 production issues.
Say it in an interview
"Driver OOM almost always comes from pulling data to the driver with collect or toPandas, an over-large broadcast, or huge file listings. I fix the cause, writing results out and keeping broadcasts small, and only increase driver memory as a last resort."

Disk spill

Symptom

The stage is slow but doesn't fail. Spill (Memory) and Spill (Disk) are non-zero, often several times the shuffle read size.

Metric (example)Min25thMedian75thMax
Shuffle read1.8 GB2.0 GB2.1 GB2.2 GB2.4 GB
Spill (memory)5 GB6 GB6.4 GB6.8 GB7.5 GB
Spill (disk)1.1 GB1.3 GB1.4 GB1.5 GB1.7 GB

Why it happens

A sort, join or aggregation needed more execution memory than its task had, so Spark wrote sorted runs to local disk and merged them later. Spill (Memory) is the in-memory (deserialised) size of what was spilled; Spill (Disk) is the serialised size written, which is why it's smaller.

How to confirm

  1. Divide the stage's shuffle read by its tasks: here about 2 GB per task, far above 100–200 MB.
  2. Check whether spill is even across tasks (partitions too big) or concentrated in a few (skew).
  3. Work out memory per task: execution pool ÷ cores per executor (Module 1 deep dive).

Fix

  • More partitions: raise spark.sql.shuffle.partitions (here about 10×), or rely on AQE with a smaller advisory size. Size it with the partition calculator.
  • Fix skew if spill sits in a few tasks.
  • More memory per task: fewer cores per executor, or memory-optimised instances.
  • Shrink rows: select fewer columns before the shuffle; aggregate before exploding.
  • Fast local disks (NVMe) for shuffle-heavy workloads.
spark.conf.set("spark.sql.shuffle.partitions", 2000)   # ~200 MB per partition
spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "128m")

Prevent

  • Revisit shuffle partitions when input volume grows; a setting tuned for last year's data spills on this year's. With AQE, set the initial number high and let coalescing reduce it.
Say it in an interview
"Spill means a task's sort or aggregation didn't fit in its execution memory. I look at shuffle read per task and spill size; if partitions are around 2 GB, I raise shuffle partitions so each is about 128–200 MB. If spill sits in a few tasks it's skew; otherwise I give tasks more memory with fewer cores per executor or larger instances."

Small files

Symptom

Reading a table takes minutes before any task starts; the scan stage has tens of thousands of tasks of a few hundred milliseconds; writes produce thousands of tiny files.

Files in table (example)48,000
Average file size300 KB
Median task duration0.3 s

Why it happens

Each file costs a listing call, an open and a footer read, which dominate when files are tiny. Causes: frequent streaming or micro-batch writes, partitionBy on high-cardinality columns, too many shuffle partitions at write time, and many small appends.

How to confirm

  1. Check file count and average size: DESCRIBE DETAIL on Delta (numFiles, sizeInBytes), or list the path.
  2. Check partitioning: thousands of partition folders with one small file each?
  3. Check the task count of the writing job's final stage.

Fix

  • Compact: OPTIMIZE on Delta (or rewrite_data_files on Iceberg), on a schedule.
  • Prevent at write time: optimized writes / auto-compaction, or repartition by the partition column before writing.
  • Partition only on low-cardinality columns (date, not customer id); use clustering for the rest.
  • On read, Spark already packs small files into splits up to spark.sql.files.maxPartitionBytes (128 MB), charging openCostInBytes (4 MB) per file, but the listing and open cost remain.
OPTIMIZE gold.events;   -- Delta compaction
ALTER TABLE gold.events SET TBLPROPERTIES (
  'delta.autoOptimize.optimizeWrite' = 'true',
  'delta.autoOptimize.autoCompact'   = 'true');

Prevent

  • Set write-time compaction on every streaming or frequently appended table, schedule OPTIMIZE, and alert when average file size drops below a threshold.
Say it in an interview
"Small files hurt because listing, opening and footer reads dominate. I fix existing tables with compaction and prevent new ones at write time with optimized writes or by repartitioning on the partition column, and I avoid high-cardinality partition columns."

Heavy shuffle / slow join

Symptom

A join stage shuffles hundreds of GB. The plan shows SortMergeJoin with a table you know is small, or several Exchanges on the same key.

Shuffle write, join stage (example)620 GB
Join strategySortMergeJoin
Exchange nodes in plan4

Why it happens

Both sides of a sort-merge join are shuffled and sorted. If one side is small, filters weren't pushed down, or columns weren't pruned, most of that movement is wasted.

How to confirm

  1. Count Exchange nodes in the final plan (SQL tab).
  2. Check each join input's size after filters: could one be broadcast?
  3. Check PushedFilters and ReadSchema on the scans (Module 4).
  4. Look for repeated shuffles on the same key, or an unnecessary distinct / orderBy.
df.explain("formatted")

Fix

  • Broadcast the small side (hint or higher threshold).
  • Filter and project before the join; pre-aggregate the fact table.
  • Remove unnecessary distinct / orderBy / repartition. Full checklist: reducing shuffle.
  • Bucket or co-locate large tables joined repeatedly on the same key.
  • Keep AQE on so it can switch join strategy and coalesce partitions.
dim_small = dims.filter("active = true").select("cust_id", "segment")
result = (orders.select("cust_id", "amount", "dt")
                .filter("dt >= '2026-09-01'")
                .join(F.broadcast(dim_small), "cust_id"))

Prevent

  • Review explain() for new pipelines; keep table statistics fresh (ANALYZE TABLE) so the planner sees real sizes.
Say it in an interview
"I count the Exchanges in the final plan and check the size of each join input. Usually the fix is to read less with pushdown and pruning, broadcast the small side, pre-aggregate before joining, and remove accidental shuffles, with AQE left on to adapt at runtime."

"Nothing changed, but it's four times slower"

The scenario

A nightly job went from 1 hour to 4 hours. Nobody changed the code. This is the most common interview framing, because it tests the whole debug flow rather than one fix.

How to work it

  1. Compare with a good run. Open both in the Spark UI (or the history server) and find which stage grew. Don't tune the whole job.
  2. Input volume. Did the source grow, or did a filter stop pruning (a new partition scheme, a changed predicate type)?
  3. Task-time distribution. A new hot key means skew.
  4. Spill. The data outgrew the memory per task at the same partition count.
  5. File counts. Small files accumulating in a source table.
  6. Join strategy. A dimension crossed the broadcast threshold and became a sort-merge join.
  7. Environment. A runtime upgrade, a smaller instance type, spot capacity loss, or a noisy neighbour on shared compute.
Say it in an interview
"I wouldn't start changing settings. I'd compare the slow run with a good one stage by stage, find the stage that grew, then check input volume, skew, spill, file counts and the join strategy for that stage. Once I've fixed the cause, I'd add monitoring on input size and stage duration so we see the next drift before it becomes an incident."

Common interview questions

199 tasks finish in 30 s, one takes 45 min. Fix it three ways.
AQE skew-join handling (if it's a sort-merge join and AQE is on), broadcast the smaller side, or salt the hot key. First check whether the hot key is NULL or a default value that should be filtered out.
Heap OOM vs container killed: what's the difference?
Heap OOM is the JVM running out of heap: too much data per task, so use more partitions or more memory per task. Container killed (exit 137) means total process memory exceeded the container limit, usually off-heap, native or Python memory: raise memoryOverhead or reduce Python memory use.
Is spill always bad?
No. Spill means Spark survived memory pressure instead of failing. A little is fine; spill that's a large multiple of shuffle read, or that appears on every task, means partitions are too big for the memory per task.
Your write produces 20,000 small files. Options?
Repartition before the write (by the partition column if using partitionBy), enable optimized writes or auto-compaction on Delta, run OPTIMIZE, and stop partitioning on high-cardinality columns.
When would raising driver memory be the right fix?
Rarely: when the driver legitimately holds a lot, such as planning over a huge number of files or partitions, or a deliberately broadcast medium table. If the cause is collect or toPandas on big data, more driver memory only delays the failure.
