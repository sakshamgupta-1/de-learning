Reducing shuffle: the checklist

Every shuffle writes data to local disk, sends it over the network and usually sorts it. Work down this list in order; the first items save the most.

  1. Read less. Filter and select columns as early as possible, and make sure filters reach the scan (PushedFilters, PartitionFilters in Module 4).
  2. Broadcast small sides. Raise autoBroadcastJoinThreshold or add a hint for dimension tables up to a few hundred MB, within driver and executor memory.
  3. Pre-aggregate before joining. Aggregate the fact table to the grain you need, then join the smaller result.
  4. Remove accidental shuffles (see the table below).
  5. Shuffle once, reuse. Consecutive joins or aggregations on the same key reuse the existing partitioning. Bucketing, or co-located clustering, avoids the shuffle for large tables joined repeatedly on the same key.
  6. Right-size what's left. Let AQE coalesce, or set spark.sql.shuffle.partitions so each shuffle partition is roughly 100–200 MB (calculator).

repartition vs coalesce

Both change the number of partitions. repartition is a wide transformation: a full shuffle that produces evenly sized partitions. coalesce is narrow: it merges neighbouring partitions without a shuffle, so it's cheap but keeps any unevenness. Switch between them on the same six input partitions:

repartition(n) / repartition(col)coalesce(n)
ShuffleYes (wide, new stage)No (narrow, same stage)
DirectionIncrease or decreaseDecrease only (asking for more is a no-op)
ResultEven sizes; by column, the same key lands in the same partitionUneven if the inputs were uneven
Use forFixing too few or skewed partitions, more parallelism, laying out data before a partitionBy writeCutting the number of output files cheaply after a selective filter

Related: repartitionByRange(col) range-partitions by sampled boundaries (sorted, contiguous ranges per partition), and the REBALANCE SQL hint asks AQE to even out partition sizes before a write.

The coalesce(1) trap

Because coalesce adds no stage boundary, its reduced parallelism applies to the whole stage it sits in, not just the write. Take df.groupBy("k").agg(...).coalesce(1).write…:

If the work before the final write is heavy, repartition(1) is faster: it costs one small extra shuffle but keeps the heavy work parallel. Better still, ask whether you need a single file at all.

Cache vs persist

  • cache() is persist() with the default level: MEMORY_ONLY for RDDs, memory-and-disk for DataFrames (MEMORY_AND_DISK; PySpark reports it as MEMORY_AND_DISK_DESER).
  • Caching is lazy: nothing is stored until an action runs. The Storage tab shows what's cached and what fraction fits.
  • Cached blocks live in the storage pool of unified memory and can be evicted when execution needs room (Module 1).
  • Call unpersist() when done.
Storage levelWhereUse when
MEMORY_ONLYHeap; partitions that don't fit are recomputedSmall, hot RDDs that are cheap to recompute
MEMORY_AND_DISKHeap, overflow to local diskThe usual choice for DataFrames
DISK_ONLYLocal diskLarge and expensive to recompute, memory is tight
*_SER (Scala/Java)Serialised in memoryLess memory, more CPU. DataFrame caches are already compact columnar
*_2Replicated on two executorsLosing an executor must not force recomputation
OFF_HEAPOff-heap memoryLarge caches without GC pressure; needs off-heap memory configured

When caching pays off, and when it doesn't

  • Cache when a DataFrame is reused by several actions and is expensive to recompute (joins, heavy parsing, remote sources).
  • Don't cache something used once, or cheap to re-read from columnar files: caching costs a full materialisation and memory that execution could use.
  • To cut long lineage in iterative jobs, use checkpoint() (reliable storage) or localCheckpoint() (executor-local, faster, lost with the executor), or write an intermediate table.
Not on Databricks serverless
On serverless compute, cache(), persist(), unpersist() and checkpoint() raise errors. Write an intermediate table, or restructure so the data is read once. Databricks' disk cache still speeds up repeated Parquet and Delta reads automatically.

GC and Python overhead

Garbage collection

  • Signal: the Executors tab highlights GC time over about 10% of task time; the task table has a GC Time column.
  • Causes: too much data per task, caching deserialised objects, RDD code creating many objects, very large heaps.
  • Fixes: smaller partitions; DataFrames instead of RDDs (Tungsten stores rows as compact binary, not objects); smaller executors; G1GC (the default collector on modern JVMs) for large heaps.

Python

  • Plain Python UDFs move every row from the JVM to a Python worker and back, one row at a time. Prefer built-in functions; use pandas UDFs (Arrow batches) when you need Python. Details in Module 2.
  • Python workers use memory outside the JVM heap, counted against memoryOverhead. A container killed with healthy heap usage often means Python memory.
  • On the driver, collect() and toPandas() pull everything into one process (driver OOM).

Check yourself

You filter 1 TB down to 5 GB and write it. It produces 8,000 tiny files. Fix?
coalesce(n) before the write: the filter left the data in the original 8,000 partitions, and coalescing merges them without a shuffle. Choose n for files of roughly 128 MB–1 GB (here about 20–40).
When is repartition(col) before a write the right call?
When writing with partitionBy(col): without it, every task can write a file into every partition folder (tasks × folders files). Repartitioning by the same column puts each folder's rows in few tasks.
A DataFrame is cached but the Storage tab shows 40% cached. What does that mean?
Only 40% of the partitions fit (or survived eviction). With MEMORY_ONLY the rest are recomputed on each use; with MEMORY_AND_DISK they'd be on disk. Either cache less (fewer columns, filtered first) or give storage more room.
Your pipeline runs on serverless and uses df.cache() to avoid reading a source twice. What now?
It will fail on serverless. Write the expensive intermediate result to a table and read it back, or restructure into one pass (for example, a window instead of a self-join).
