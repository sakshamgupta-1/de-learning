Size it, then fix the skew

Two calculators for the numbers interviewers ask you to work out on a whiteboard, and a side-by-side run that shows why salting a hot key shortens a stage.

Partition sizing

Rule of thumb: roughly 100–200 MB per shuffle partition, and at least 2–3 tasks per core so a slow task doesn't leave cores idle. Rounding the count to a multiple of the cores keeps the last wave full (waves are explained in Module 1).

spark.conf.set("spark.sql.shuffle.partitions", 4000)
# with AQE on, you can instead set a high initial number and a target size:
spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "128m")

The shuffle size to plug in is the stage's Shuffle Write in the Spark UI, not the input file size: compressed columnar files grow when decoded into rows.

Executor sizing

The classic YARN/Kubernetes recipe: about 5 cores per executor (good I/O throughput without too many threads sharing one heap), 1 core and about 1 GB per node left for the OS and daemons, and about 10% of executor memory for overhead (spark.executor.memoryOverhead defaults to 10%, minimum 384 MB).

One executor is subtracted for the YARN application master in cluster mode. Execution memory per task uses the defaults spark.memory.fraction=0.6 and storageFraction=0.5, ignoring the 300 MB reserved: an approximation. On Databricks classic compute there's one executor per worker, so you choose instance type and worker count; on serverless you don't size executors at all.

How to choose, in an interview

  • Too-fat executors (one executor × 15 cores × 60 GB): long GC pauses on a big heap, and storage-client contention with many threads.
  • Too-thin executors (1 core each): every executor holds its own copy of broadcasts, more JVM overhead, and more executors for the driver to track.
  • Memory-hungry stages (big joins, wide rows): fewer cores per executor or memory-optimised instances, so each task gets more memory.
  • CPU-bound stages (parsing, UDFs, compression): compute-optimised instances, more cores.
  • Variable load: dynamic allocation or autoscaling with sensible minimum and maximum (Module 1 deep dive).

Salting a hot key

One key holds a large share of the rows, so after the shuffle one task does most of the work and the stage waits for it. Salting adds a random number (0 to N−1) to the hot side's key, so that key's rows spread over N partitions, and copies each row of the other side N times so every salted key still finds its match. The total work is the same in both runs. What changes is that no single task is longer than the rest put together, so the 4 cores stay busy and the stage ends sooner. In the skewed run, three cores sit idle for most of the stage.

The code

from pyspark.sql import functions as F
N = 6   # salt buckets: enough to bring the hot key near the median partition size

# Join: salt the big (skewed) side randomly, copy the small side N times
big   = orders.withColumn("salt", (F.rand() * N).cast("int"))
small = customers.withColumn("salt", F.explode(F.array([F.lit(i) for i in range(N)])))
joined = big.join(small, ["cust_id", "salt"]).drop("salt")

# Aggregation: aggregate per (key, salt) first, then per key
partial = big.groupBy("cust_id", "salt").agg(F.sum("amount").alias("s"))
final   = partial.groupBy("cust_id").agg(F.sum("s").alias("amount"))
  • Cost of salting a join: the small side grows N times. Salt only the hot keys (salt 0 for everything else) when the small side isn't tiny.
  • Two-step aggregation works for sums, counts, min and max. Averages need sum and count carried separately; exact distinct counts don't combine this way.
  • Try the cheaper fixes first: filter NULL or default keys, let AQE split skewed sort-merge join partitions, or broadcast the small side. Salting is for when those don't apply. See data skew in production.

Check yourself

A stage shuffles 1 TB and you have 200 cores. How many shuffle partitions?
At about 128 MB each, 1 TB ÷ 128 MB ≈ 8,192. Rounded to a multiple of 200 cores that's 8,200, about 41 waves. Anything from about 5,000 to 10,000 is defensible; 200 (the default) would make 5 GB partitions and spill heavily.
Why not one executor per node with all 16 cores?
One huge heap means long GC pauses, and 16 threads sharing one storage client can bottleneck I/O. Around 4–5 cores per executor is the usual balance. On Databricks classic compute this choice is made for you (one executor per worker), so you tune instance type instead.
You salt with N = 100 and the job gets slower. Why?
The small side was copied 100 times, so the join input grew a lot, and the shuffle now has many more rows. Pick N so the hot key's share comes down to about the median partition size, and salt only the hot keys.
