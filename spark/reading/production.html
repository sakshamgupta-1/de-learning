When the read is the bottleneck

Eight ways the first stage of a job goes wrong, across databases, files and APIs. Each follows symptom → why → confirm → fix → prevent → interview answer.

A JDBC read runs as one task

Symptom

Extracting a large table takes hours; the scan stage has 1 task while the rest of the cluster idles. Later stages may OOM on the single huge partition.

Why it happens

Without partitionColumn/bounds/numPartitions or predicates, Spark issues one query on one connection.

How to confirm

  1. The scan stage in the Spark UI shows 1 task; df.rdd.getNumPartitions() is 1.
  2. The database shows one session running the query.

Fix

  • Add a partition column with bounds, or quantile predicates (example).
  • For very large tables, export to files and read those instead.

Prevent

  • A shared JDBC read helper that requires a partitioning strategy for tables above a size threshold.
Say it in an interview
"A JDBC read is single-threaded by default. I always give Spark a partitioning strategy, a numeric or date column with bounds, or explicit predicates, and for very large tables I prefer an export to files."

One task reads most of the table

Symptom

The JDBC read has 16 tasks, 15 finish in a minute, one runs for an hour.

Why it happens

Ranges are equal width, not equal rows. Busy recent periods, gaps in the id space, or outlier keys (bounds taken from MIN/MAX with a test row at 999,999,999) concentrate rows in one range.

How to confirm

  1. Task input rows in the stage's summary metrics: max far above median.
  2. SELECT width_bucket(id, lo, hi, N), count(*) … GROUP BY 1 on the source shows the imbalance.

Fix

  • Quantile predicates; or bounds from percentiles instead of MIN/MAX; or partition on a better-spread column (a date for time-ordered data, a hash for strings).

Prevent

  • Compute boundaries from the data (or database statistics) instead of hard-coding bounds; review them when volumes shift.
Say it in an interview
"Spark's JDBC ranges are equal width, so skewed or gappy keys give skewed tasks. I compute quantile boundaries and pass them as predicates so each task reads about the same number of rows."

The source database is overloaded

Symptom

The DBA reports CPU or I/O spikes, lock waits or "too many connections" during the extract; the application on that database slows down.

Why it happens

numPartitions queries run at once, each possibly a full table scan if the partition column or hash expression isn't indexed. Running it against the primary competes with production traffic.

How to confirm

  1. Database sessions from Spark's user during the run; execution plans of the generated range queries.

Fix

  • Read from a replica; lower numPartitions to an agreed connection budget; index the partition column; run outside peak hours.
  • Switch to incremental extracts, or a CDC feed, instead of full reads.

Prevent

  • Agree a connection and time budget with the source owner; prefer exports or CDC for large or frequent extracts.
Say it in an interview
"numPartitions is a connection count, not just a Spark setting. I read from a replica with an agreed concurrency, make sure each range query uses an index, and move frequent large extracts to CDC or exports."

Slow even with many partitions

Symptom

Plenty of tasks, the database is idle, but each task crawls; executors show little CPU.

Why it happens

Network round trips dominate: a small driver default fetchsize (Oracle fetches 10 rows per trip) means millions of trips. Wide rows with columns you don't need make it worse.

How to confirm

  1. Task time is long but rows per second per task are low; network wait on the database side.

Fix

  • Set fetchsize to thousands or tens of thousands; select only needed columns in dbtable; push filters down (check PushedFilters).

Prevent

  • Default fetchsize in your JDBC read helper; review the projected columns.
Say it in an interview
"If tasks are many but slow and the database is idle, it's round trips: I raise fetchsize, project only the needed columns, and make sure filters are pushed down."

Missing or duplicate rows after a parallel read

Symptom

Row counts don't match the source; some keys appear twice, others are missing, usually only on busy tables.

Why it happens

Each partition is a separate query at a different moment. Rows whose partition column changes between queries are read twice or not at all; inserts and deletes during the read land unevenly. Overlapping or incomplete predicates do the same deterministically.

How to confirm

  1. Duplicated keys have a recently changed partition column; or the predicates overlap or leave gaps (check boundary conditions and NULLs).

Fix

  • Partition on an immutable column; read from a snapshot or a replica at a fixed point; fix predicate boundaries; dedupe on the key.

Prevent

  • Reconcile counts against the source for each extract; never partition on updated_at or status columns.
Say it in an interview
"A parallel JDBC read is N queries at N moments, so it isn't a consistent snapshot. I partition on an immutable key, read from a snapshot or replica, and reconcile counts after the load."

Giant gzip files

Symptom

A daily file drop of a few 20 GB .csv.gz files reads with one task per file; those tasks take an hour and may spill or OOM downstream.

Why it happens

Gzip can't be split, so each file is read by one task and lands in one partition.

How to confirm

  1. Scan stage task count equals file count; task input size equals file size.

Fix

  • Ask the producer for many smaller files, or a splittable format (Parquet, or bzip2 if it must be text).
  • Until then, repartition() right after reading so later stages use the whole cluster; land the data once as Parquet or Delta and read that afterwards.

Prevent

  • Agree file format and size limits in the source's data contract.
Say it in an interview
"Gzip isn't splittable, so each file is one task. I repartition after the read to protect later stages, convert once to Parquet or Delta, and get the producer to send smaller or splittable files."

The API job fails or gets throttled

Symptom

Many HTTP 429 responses, long backoffs, or the whole job failing after hours because a handful of pages returned errors.

Why it happens

Concurrency (partitions running at once) times calls per task exceeds the API's rate limit; and raise_for_status() turns one bad page into a failed task, which Spark retries (re-calling every page in that partition) and finally fails the job.

How to confirm

  1. Status code counts per run; task failures with HTTP errors in the stage's error column.

Fix

  • Size partitions to the rate limit; retries with exponential backoff that honour Retry-After.
  • Return failures as rows (status, error) instead of raising; re-run only failed requests.

Prevent

  • Record rate limits in the source's documentation, alert on error-row counts, and test with production-sized request lists.
Say it in an interview
"Partition count is the API concurrency, so I size it to the rate limit, retry with backoff on 429s, and return errors as rows so one bad page never fails the whole job. Then I rerun just the failed requests."

The API is called again and again

Symptom

The provider reports several times more calls than pages; costs or quotas run out; numbers differ between steps of the same job.

Why it happens

The API-calling DataFrame is lazy: every action (count, display, each write) re-runs the calls. Task retries and speculative tasks add more.

How to confirm

  1. Count the jobs in the Spark UI that include the mapInPandas or mapPartitions stage.

Fix

  • Write raw responses to a Bronze table in one action, and build everything downstream from that table.
  • Keep speculation off for API jobs.

Prevent

  • Code review rule: anything with side effects or external calls is written out once, never re-derived.
Say it in an interview
"Because Spark is lazy, an API-calling DataFrame calls the API again on every action. I land the raw responses in one write and work from the table, with speculation off."
