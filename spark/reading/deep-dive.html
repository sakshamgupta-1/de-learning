How each source is split

How file splits are sized and packed

  1. Split size. maxSplitBytes = min(maxPartitionBytes, max(openCostInBytes, bytesPerCore)), where bytesPerCore is the total input size (plus 4 MB per file) divided by spark.sql.files.minPartitionNum, which defaults to the default parallelism (total cores). So on a large cluster with little data, splits shrink below 128 MB to keep every core busy.
  2. Cut. Each splittable file is cut into pieces of at most maxSplitBytes; a non-splittable file stays whole.
  3. Pack. Pieces are sorted by size, largest first, and packed into partitions until adding the next piece (plus 4 MB open cost) would exceed maxSplitBytes.
  4. Read. One task per partition. For Parquet and ORC, a split is mapped to whole row groups or stripes, so a 1 GB row group is read by one task however the split falls.

The openCostInBytes charge is why thousands of 100 KB files don't all land in one partition: each counts as at least 4 MB when packing. It doesn't remove the per-file cost of listing and opening, which is why small files still hurt (small files).

A non-splittable file is read by one task, and all its rows sit in one partition until a shuffle. If later stages are heavy, repartition() right after the read spreads them; the read itself stays as slow as the largest file.

Exactly how JDBC ranges are generated

With partitionColumn=id, lowerBound=0, upperBound=100, numPartitions=4, Spark computes a stride of upperBound/numPartitions − lowerBound/numPartitions = 25 and issues four queries:

SELECT … FROM orders WHERE id < 25 OR id IS NULL
SELECT … FROM orders WHERE id >= 25 AND id < 50
SELECT … FROM orders WHERE id >= 50 AND id < 75
SELECT … FROM orders WHERE id >= 75
  • Open ends: the first range catches everything below and NULLs; the last everything above. Nothing is filtered by the bounds.
  • Too many partitions: if numPartitions exceeds upperBound − lowerBound, Spark reduces it.
  • Dates and timestamps (Spark 2.4+): bounds are given as date or timestamp strings and the ranges are equal time intervals.
  • Strings and UUIDs can't be a partitionColumn. Use predicates, one WHERE clause per partition, which can be any condition the database accepts: ranges from quantiles, MOD(ORA_HASH(id), 16) = 3, region = 'EU', or the database's own partitions.
  • Predicates must cover every row exactly once. Spark doesn't check: overlapping clauses duplicate rows, gaps lose them.
  • Index the column. Without an index on the partition column (or expression), every one of the N queries scans the whole table.

Check what really reached the database: df.explain() shows PushedFilters and, for aggregates, PushedAggregates on the JDBC scan. On the database side, the session or query log shows the N generated queries.

Kafka offset ranges

df = (spark.read.format("kafka")
      .option("kafka.bootstrap.servers", brokers)
      .option("subscribe", "orders")
      .option("startingOffsets", '{"orders":{"0":1000,"1":1000,"2":1000}}')
      .option("endingOffsets", "latest")
      .option("minPartitions", 24)                # split big ranges over more tasks
      .load())
  • Each topic partition's offset range is one task unless minPartitions asks for more; Spark then splits the larger ranges proportionally.
  • Batch reads don't keep a checkpoint: you pass offsets (or timestamps via startingOffsetsByTimestamp) and track them yourself. A streaming read with availableNow gives the same parallelism with offsets tracked for you.
  • Messages are only readable within the topic's retention; ranges older than that fail (or are skipped with failOnDataLoss=false).

Pagination decides what can run in parallel

  • Page number or offset (?page=37): fetch page 1 for the total, generate every page number, fan them out. Data changing during the read can shift rows between pages, so dedupe on a key.
  • Cursor or next-link (?after=abc): each page needs the previous response, so one sequence runs in one task. Parallelise across independent keys instead: per customer, per day, per region.
  • Time windows (?from=…&to=…): split the period into windows and fan those out; the most parallel and the easiest to rerun.

What the executors need

  • Network access from executors to the API (firewalls and private endpoints often allow only the driver's subnet, or nothing).
  • Credentials passed into the function, from a secret store on the driver; refresh short-lived tokens per partition.
  • Rate limits shared by all tasks: concurrency × calls per second per task must stay under the API's limit. Retries with backoff honour Retry-After.
  • Idempotent calls: task retries and speculation repeat calls. Use GETs; turn speculation off for these jobs.

In every case, check explain() for what was pushed down: a filter that isn't pushed means the whole table crosses the network.

Consistency across parallel queries

N partitions means N independent queries, possibly seconds or minutes apart. Rows inserted, updated or deleted in between can be missed, read twice (if their partition column changed) or read in a mix of old and new states.

  • Read a fixed point: a read replica paused at a point in time, a database snapshot, Oracle flashback (AS OF SCN) in each predicate, or SQL Server snapshot isolation via sessionInitStatement.
  • Partition on a column that doesn't change (an id, a creation date), never on updated_at or status.
  • Export first when consistency matters and the table is large: one consistent dump to files, then a parallel file read.

Incremental extracts

  • Watermark column: read WHERE updated_at > :last_max, store the new maximum after a successful write. Overlap slightly (>= last_max − 5 min) and MERGE, so transactions committing late aren't missed. Misses hard deletes.
  • CDC: log-based capture (Debezium, GoldenGate, DMS) into Kafka or files catches deletes and every change without querying the table.
  • Partition the extract too: a large daily delta still needs predicates or a partition column to read in parallel.

Check yourself

On a 200-core cluster, 2 GB of Parquet reads with about 200 tasks, not 16. Why?
Splits shrink when data per core is small: bytesPerCore = 2 GB ÷ 200 ≈ 10 MB, which is below 128 MB, so maxSplitBytes becomes about 10 MB and Spark makes roughly 200 splits (bounded by row groups).
Why can't you pass query together with partitionColumn?
Spark needs to wrap the source in its own SELECT … WHERE range. Give the subquery as dbtable="(SELECT …) AS t" and partition on one of its columns.
A cursor-paginated API returns 10 million records. How do you parallelise it?
You can't parallelise one cursor chain. Split the request space by something independent (date ranges, customers, regions), run one cursor chain per split in parallel tasks, and land raw pages.
