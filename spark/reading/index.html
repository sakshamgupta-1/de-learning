Reading data in parallel

A Spark job is only as parallel as its first stage, and the first stage's tasks are decided by the source: file splits, JDBC ranges, Kafka partitions or the API calls you fan out. Know who decides the partitions for each source and what makes them uneven, and most "the read is slow" questions answer themselves. A 10-minute refresher.

Who decides how many read tasks there are?

Every later stage can be resized with a shuffle, but the scan stage gets exactly as many tasks as the source offers input partitions. Each source has its own rule: files are split by size, a JDBC table by the ranges you configure (one, if you configure none), Kafka by topic partition, and an API by the request list you build. If the source gives one big partition, one task does all the reading, however big the cluster.

Two problems follow from that rule. Too few partitions leave cores idle. Uneven partitions, from skewed key ranges, a giant gzip file or a hot Kafka partition, leave one task running long after the rest. The fixes happen at the source boundary: how you split the read, not how you tune the stages after it.

Source by source

The same idea for four sources: source units on the left, the read tasks they become on the right. Red marks the unit that holds the stage up.

Files

  • Splits: Spark cuts files into splits of up to spark.sql.files.maxPartitionBytes (128 MB) and packs small files together, charging openCostInBytes (4 MB) per file. One split, one task.
  • Splittable or not: Parquet, ORC, uncompressed or bzip2 CSV/JSON lines can be split. Gzip files, and multiLine JSON or CSV, can't: each is one task, whatever its size.
  • Uneven layouts: one huge partition folder, a few giant files among small ones, or Parquet written with very large row groups (a Parquet split is assigned whole row groups).

Databases (JDBC)

A plain spark.read.jdbc(url, "orders") runs one query on one connection in one task. To read in parallel, give Spark a way to split the table:

orders = (spark.read.format("jdbc")
    .option("url", url).option("dbtable", "sales.orders")
    .option("partitionColumn", "order_id")         # numeric, date or timestamp; ideally indexed
    .option("lowerBound", 1).option("upperBound", 50_000_000)
    .option("numPartitions", 16)                    # 16 queries, 16 connections at once
    .option("fetchsize", 10_000)                    # rows per network round trip
    .load())
  • Spark cuts [lowerBound, upperBound) into numPartitions ranges of equal width. The bounds don't filter: the first range also takes everything below it (and NULLs), the last everything above.
  • Equal width is not equal rows. Clustered ids, gaps or a few outliers (a test row with id 99,999,999) make one task read most of the table. Pass a predicates list with your own ranges instead: see the calculator.
  • numPartitions is also the number of concurrent connections to the database. Read from a replica, and agree the number with the DBA.
  • Each partition is its own query, possibly at a different moment: rows can move between ranges mid-read. For a consistent copy, read a snapshot, a replica or an export.

Kafka (batch reads)

spark.read.format("kafka") with startingOffsets and endingOffsets reads a fixed offset range: by default one task per topic partition. A hot partition makes one long task; minPartitions splits large offset ranges across more tasks. Streaming reads follow the same mapping per micro-batch, covered in the Structured Streaming path.

REST APIs

Spark has no built-in parallel API reader. A loop on the driver is serial. To parallelise, build a DataFrame of request parameters (pages, ids, dates), repartition it to the concurrency the API allows, and call the API inside each task with mapInPandas (or rdd.mapPartitions on classic compute). Land the raw responses in Bronze straight away: the read is lazy, so every action would otherwise call the API again.

raw = (spark.range(1, 501).withColumnRenamed("id", "page")
            .repartition(10)                            # 10 concurrent callers = 10 partitions
            .mapInPandas(fetch_pages, "page long, status int, body string, error string"))
raw.write.mode("append").saveAsTable("bronze.api_raw")

Full version with retries, rate limiting and error rows: examples. A reusable connector can be written with Spark 4.0's Python data source API.

Say it in an interview

The principle
"The scan stage's parallelism comes from the source, not the cluster: file splits, JDBC ranges, Kafka partitions, or the request list I fan out to an API. So I make sure the source is split into enough, evenly sized pieces, because a shuffle afterwards can't speed up a read that one task is doing."
JDBC
"A JDBC read is one query on one connection unless I set partitionColumn, bounds and numPartitions, or pass predicates. The ranges are equal width, so with skewed or gappy keys I compute quantile boundaries and pass them as predicates. numPartitions is also the connection count, so I read from a replica, set fetchsize, and for big tables I'd rather export to files and read those."
APIs
"I build a DataFrame of request parameters, repartition it to the concurrency the API's rate limit allows, and call the API in mapInPandas with retries and backoff. Failures come back as rows, not exceptions, and I land the raw responses in Bronze immediately, because the read is lazy and would call the API again on every action."

Quick check

A JDBC read of a 200 million row table runs as a single task on a 64-core cluster. Why?
No partitioning options were set, so Spark issued one query on one connection. Set partitionColumn, bounds and numPartitions, or pass predicates.
You set lowerBound=1, upperBound=1000 on a table with ids up to 10 million. Are rows above 1,000 lost?
No. The bounds only shape the ranges; the last partition reads everything above its start. But nearly all rows land in that last partition, so the read is effectively single-task.
A folder of 50 gzip CSV files, 4 GB each, reads with only 50 tasks. Can maxPartitionBytes help?
No: gzip can't be split, so each file is one task. Recompress as a splittable format (Parquet with snappy or zstd, or bzip2), or repartition right after reading so later stages use the cluster.
Your API job repartitions 500 page numbers into 10 partitions on a 4-core cluster. How many calls run at once?
Four: only 4 task slots exist, so at most 4 partitions run concurrently. Concurrency is the smaller of the partition count and free task slots.
Why can the same JDBC read return a row twice, or miss one?
Each partition is a separate query. If a row's partition column changes between the queries, it can be read by two ranges or by none. Read from a snapshot, a replica at a fixed point, or an export.
