From your code to running tasks

How Spark turns Python into work on the cluster: transformations build a plan, actions run it, shuffles cut it into stages, and partitions become tasks. A 10-minute refresher.

The flow in five steps

  1. Start. spark-submit (or a notebook) starts the driver, which gets executors from the cluster manager.
  2. Describe. Your code runs on the driver. Each transformation only adds a step to a logical plan; no data moves.
  3. Trigger. An action (write, count, collect, show) creates a job.
  4. Plan. Catalyst optimises the plan; the DAG scheduler cuts it into stages at every shuffle.
  5. Run. Each stage runs one task per partition on executor cores; stages run in dependency order until the job ends.

Lazy evaluation: per action, not per script

Transformations don't run anything; they extend a DataFrame's plan (its lineage). Your Python still runs line by line. When the interpreter reaches an action, that line blocks: Spark optimises that DataFrame's lineage so far, runs it as a job, and returns. Spark never reads ahead in your script.

orders = spark.read.parquet("s3://lake/orders")    # metadata only
ae     = orders.filter("country = 'AE'")           # plan grows, instant
n      = ae.count()                                # Job 1 runs now; Python waits
if n > 0:                                          # plain Python
    ae.groupBy("segment").sum("amount") \
      .write.saveAsTable("gold.sales")             # Job 2: re-reads orders from scratch

Because it's lazy, Spark can optimise a whole chain at once (push filters into the scan, fuse narrow steps). Because it's per action, every action recomputes its lineage unless you cache. Timeline and the exceptions →

Narrow vs wide transformations

A narrow transformation builds each output partition from one input partition, so no data moves between machines. A wide one needs rows from many partitions, so Spark shuffles data across the network, and that's where a new stage starts.

Jobs, stages and tasks

One action → one job. The DAG scheduler walks the plan back from the result and starts a new stage at every shuffle (shown as Exchange in plans). Each stage runs one task per partition. Here's one job that filters orders, joins customers, sums by segment and writes the result:

Say it in an interview

Lazy evaluation
"Python executes line by line on the driver. Transformations only extend a DataFrame's logical plan; when the interpreter reaches an action, Spark optimises that lineage, runs it as one or more jobs and blocks until it returns. It never looks ahead, so each action recomputes its lineage unless it's cached."
Jobs, stages, tasks
"An action creates a job. The DAG scheduler starts a new stage at every shuffle dependency, so stages are runs of narrow transformations pipelined together. Each stage runs one task per partition, so partitions decide parallelism."
Narrow vs wide
"Narrow transformations like filter and select work within a partition and are pipelined in one stage. Wide ones like groupBy, distinct and most joins need rows from many partitions, so they shuffle data over the network and create a stage boundary. A broadcast join avoids shuffling the large side."

Quick check

How many jobs: df = spark.read.parquet(p); df.count(); df.filter(...).write.parquet(q)?
At least two, one per action. The read may add a small listing job. Both actions read the files, unless df is cached.
Where exactly is a stage boundary created?
At every wide (shuffle) dependency, an Exchange in the physical plan. Narrow operations either side are pipelined into the same stage.
Is coalesce narrow or wide?
Narrow: it merges existing partitions without a shuffle. repartition is wide.
Does Spark run your whole script lazily as one plan?
No. Laziness is per DataFrame. Python runs normally, and each action runs immediately, blocking until its job finishes.
What happens when a task fails?
It's retried, up to 4 attempts by default. If shuffle files from an earlier stage were lost with an executor, the missing parent tasks are recomputed from lineage first.
