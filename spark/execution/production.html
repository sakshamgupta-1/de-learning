When lazy execution bites

Problems that come from how Spark plans and runs jobs, rather than from memory or data size. Each follows the same path: symptom, why, how to confirm, fix, prevention, interview answer.

The same data is read and computed again and again

Symptom

A pipeline takes two or three times longer than its data size suggests. The Spark UI shows the same file scan in several jobs, each with the full input size.

Why it happens

  • Every action re-runs its DataFrame's lineage from the source. A DataFrame used by three writes is computed three times.
  • Expensive steps (joins, wide aggregations, UDFs) upstream of several outputs are repeated each time.

How to confirm

  1. SQL / DataFrame tab: identical scan and join sub-plans in several queries.
  2. Input size summed across jobs is a multiple of the table size.

Fix

  • Cache the shared DataFrame before the first action, and unpersist() after the last.
  • For long or heavy shared steps, write an intermediate table once and read it in later steps; this also makes reruns cheaper.
  • Combine outputs: one partitionBy write instead of a loop of filtered writes.
enriched = orders.join(customers, "cust_id").filter("status = 'PAID'").cache()
enriched.groupBy("segment").sum("amount").write.saveAsTable("gold.by_segment")
enriched.groupBy("country").sum("amount").write.saveAsTable("gold.by_country")
enriched.unpersist()

Prevent

  • When one DataFrame feeds several outputs, decide on purpose between recompute, cache and an intermediate table.
Say it in an interview
"Spark is lazy per action, so every action recomputes its lineage. When one expensive DataFrame feeds several outputs I cache it, or write it once as an intermediate table, and I make sure to unpersist afterwards."

Debug actions left in production code

Symptom

Extra jobs labelled count, show or collect appear before the real write, each doing a full pass over the data. Runtime is far above what the final write needs.

Why it happens

print(df.count()), df.show() and similar lines added during development are real actions. Each one runs the whole lineage. Logging row counts at every step can double or triple a job's runtime.

Fix

  • Remove them, or guard them behind a debug flag.
  • Get counts from the write itself where possible (Delta table history, the SQL tab's "rows output", or write metrics) instead of an extra pass.
  • If you need a count and the data, cache first so the count and the write share one computation.
Say it in an interview
"Things like count and show are actions, so each one runs the full lineage. In production I remove debug actions or put them behind a flag, and take row counts from write metrics or table history instead."

Huge plans from loops

Symptom

java.lang.StackOverflowError
    at org.apache.spark.sql.catalyst.trees.TreeNode...

Or the driver spends minutes "planning" before any task runs, with the Spark UI idle.

Why it happens

  • Calling withColumn hundreds of times in a loop, or unioning DataFrames in a loop, builds a very deep plan. Each call also triggers re-analysis of the whole plan, so planning time grows quickly.
  • Iterative algorithms that reuse the previous iteration's DataFrame grow lineage every round.

Fix

  • Add many columns in one call: select with a list, or withColumns with a dict (Spark 3.3+).
  • Union a list at once with functools.reduce over a small number of inputs, or read them as one source.
  • In iterative jobs, cut lineage every few rounds with checkpoint(), localCheckpoint(), or by writing and re-reading.
# before: 300 withColumn calls, 300 plan re-analyses
for c in cols:
    df = df.withColumn(c, F.trim(F.col(c)))

# after: one projection
df = df.select(*[F.trim(F.col(c)).alias(c) if c in cols else F.col(c) for c in df.columns])
Say it in an interview
"Building a DataFrame in a long loop, like hundreds of withColumn calls, creates a huge plan that's slow to analyse and can overflow the stack. I build the columns in a single select, and in iterative jobs I truncate lineage with checkpoints."

Fetch failures and stage retries

Symptom

org.apache.spark.shuffle.FetchFailedException: Failed to connect to host-12/10.0.4.12:7337
Stage 7 (shuffle map stage) resubmitted due to fetch failure

Stages show as retried; earlier stages run again; total runtime balloons.

Why it happens

A stage's tasks fetch shuffle files written by the previous stage's executors. If one of those executors died (OOM, spot reclaim, node failure, long GC), its shuffle files are gone. Spark must rerun the parent stage's tasks that produced them, using lineage, before continuing.

How to confirm

  1. Stages tab: retried stage attempts; failed tasks mention FetchFailed.
  2. Executors tab: lost or removed executors around the same time, and why.

Fix

  • Fix why executors die: memory (see Module 1 failures), GC, or preemption.
  • Keep shuffle files available after executor loss: external shuffle service, or graceful decommissioning with block migration on spot or Kubernetes.
  • Use more reliable nodes for shuffle-heavy jobs.
Say it in an interview
"A FetchFailedException means shuffle output from an earlier stage is no longer reachable, usually because its executor died. Spark recomputes the missing parent tasks from lineage. I fix the executor loss itself, and use a shuffle service or decommissioning so shuffle files survive."

Job aborted after four task failures

Symptom

Job aborted due to stage failure: Task 112 in stage 3.0 failed 4 times,
most recent failure: ... java.lang.NumberFormatException: For input string: "N/A"

Why it happens

A task is retried up to spark.task.maxFailures (4) times. If the cause is deterministic (a bad record, a parsing bug, a failing UDF), every retry hits the same row and fails, so the job aborts. Retries only help with transient causes such as a flaky node or network blip.

How to confirm

  1. Read the most recent failure's exception, not just "failed 4 times".
  2. Same task index failing each attempt on different executors means it's the data, not the machine.

Fix

  • Find and handle the bad records: try_cast in SQL (Spark 3.2+) or casts that return NULL, explicit validation, or quarantine rows that fail rules.
  • For file sources, read in PERMISSIVE mode with a corrupt-record column (or badRecordsPath on Databricks) instead of failing the job.
  • Make UDFs defensive about NULLs and unexpected values.
Say it in an interview
"Task retries help only with transient failures. If the same task fails four times on different executors it's deterministic, usually a bad record, so I read the root exception, find the row, and handle it with safe casts, permissive parsing or a quarantine table."

Errors that surface far from their cause

Symptom

A failure is reported at the final write on line 300, but the cause is a cast, UDF or division written on line 40. The stack trace points into generated code, not your line.

Why it happens

Because execution is lazy, data-dependent errors only happen when an action actually processes rows, so they're reported at that action. Everything in the lineage runs inside the same stage, so the trace doesn't say which of your lines produced it. With Spark Connect, even analysis errors such as a wrong column name move to the action.

Fix

  • Bisect: add a temporary action (.limit(1000).collect()) after suspected steps, in a notebook or test, to find where it breaks.
  • Unit-test transformation functions on small DataFrames so data errors show up near their cause.
  • With ANSI mode (spark.sql.ansi.enabled, on by default since Spark 4.0), invalid casts and overflows raise errors that name the expression instead of silently producing NULLs.
Say it in an interview
"Lazy execution means data errors appear at the action, not where they're written. I keep transformations in small, unit-tested functions, and when debugging I bisect with temporary limited actions until I find the failing step."

Case study: per-file header values read on the driver

The setup

An Auto Loader stream (readStream, CSV) loads files from S3 into a Bronze table. The framework adds a file-generated timestamp column, normally parsed from the file name (<source_id>_<object>_<yyyyMMddHHmmss>.csv). One source instead puts the timestamp as the last field of the header line. The first implementation used a Python function on the driver to open each file in the S3 location, read its first line, build a file → timestamp map, broadcast it, and join it to the Auto Loader DataFrame.

Symptom

Runtime grows steadily as the bucket accumulates files, even though daily volume is flat. The driver is busy while executors sit idle at the start of every batch.

Why it happens

  • Serial work on one machine. The driver lists the location and opens files one after another; executors don't help.
  • Cost tracks the total file count, not new files. Re-reading headers of files already ingested makes every batch slower than the last.
  • Every file is read twice: once for the header, once by Auto Loader for the data.
  • A growing broadcast map is rebuilt and shipped to every executor each batch.
  • In directory listing mode, Auto Loader's own discovery also slows as the location grows.

How to confirm

  1. Spark UI: a long gap before the first job of each batch with no running tasks (driver-only work).
  2. Driver logs or profiling show S3 calls proportional to total files, not to the batch's new files.
  3. Batch duration plotted against total file count rises in a straight line.

Background: what an Auto Loader micro-batch is

Auto Loader is a Structured Streaming source, so it runs as a loop of micro-batches. Each one is an ordinary Spark batch query over a slice of new files:

Streaming query     runs until stopped (or until the backlog is done with availableNow)
└─ Micro-batch      batch_id 0, 1, 2 … = a set of NEW files, up to maxFilesPerTrigger (1,000)
   └─ Job(s)        one per action on that batch; each write inside foreachBatch is 1+ jobs
      └─ Stage      split at every shuffle
         └─ Task    one per input split: small files packed together, large uncompressed files split
  1. Discover new files (directory listing or file notifications).
  2. Cap them at cloudFiles.maxFilesPerTrigger / maxBytesPerTrigger: 2,500 new files at the default = 3 micro-batches.
  3. Record the batch's file list in the checkpoint's offset log before processing, so a failed batch is replayed with exactly the same files.
  4. Run it: foreachBatch receives a static DataFrame of those files; every action inside it creates jobs, stages and tasks as usual.
  5. Commit to the commit log once the sink succeeds, then start the next batch.

The guarantee this case study relies on is at batch level: Auto Loader never splits one file across micro-batches. It isn't at task level: within a batch, one large file can be read by several tasks.

Fix 1 (always correct): use the header row Spark already reads

Read with header=false so the header line arrives as a normal row, recognise it by its content, take its last field, and copy it to the same file's rows. Auto Loader never splits one file across micro-batches, so a file's header and data rows are always in the same batch. One read of the files, nothing on the driver, nothing that grows. The cost is a shuffle: the window moves every row of the batch by file_path and sorts within each partition.

from pyspark.sql import functions as F, Window

HEADER_FIRST = "SOURCE_ID"     # text of the header's first field
per_file = Window.partitionBy("file_path")

def enrich(batch, batch_id):
    is_header = F.col("c0") == HEADER_FIRST
    (batch
       .withColumn("file_generated_ts",        # the header's last field, copied to every row of its file
                   F.to_timestamp(F.max(F.when(is_header, F.col("c_last"))).over(per_file),
                                  "yyyyMMddHHmmss"))
       .where(~is_header)                      # drop the header row itself
       .drop("c_last")
       .write.mode("append").saveAsTable("bronze.orders"))

(spark.readStream.format("cloudFiles")
     .option("cloudFiles.format", "csv")
     .option("header", "false")               # keep the header line as a row
     .schema(raw_schema)                      # all strings; trailing c_last holds the header's extra field
     .load(src_path)
     .withColumn("file_path", F.col("_metadata.file_path"))
     .writeStream.foreachBatch(enrich)
     .trigger(availableNow=True)              # process the backlog, then stop; required on serverless
     .option("checkpointLocation", checkpoint)
     .start())
  • Why a window, not a self-join: deriving a headers DataFrame and a rows DataFrame from the same batch and joining them makes Spark scan the batch's files twice, once per side; scans aren't shared. The window reads the files once and shuffles rows by file_path so each file's header meets its rows.
  • Why a batch-wide step, not per-task logic: a large uncompressed CSV can be split into several tasks within the batch, and only the task reading the file's first block sees the header row. Grouping by file_path brings each file's timestamp to all its rows, whichever task read them. If you can guarantee files are never split, Fix 3 skips the shuffle. (How a micro-batch maps to jobs and tasks)
  • On classic compute you can instead batch.persist(), build the small headers DataFrame, and F.broadcast()-join it to the rows (unpersist in a finally). That avoids shuffling every row. It doesn't work on serverless, where cache(), persist(), unpersist() and checkpoint() raise errors. The F.broadcast() join hint itself works on both.
  • Triggers: serverless notebooks and jobs support only availableNow (or the deprecated once); the default and processingTime triggers are rejected. Lakeflow pipelines manage triggers themselves and aren't affected.
  • Identify the header by known header text, not by row order. Cast data columns to real types after the join.
  • foreachBatch can replay a batch after a failure: make the write idempotent (Delta txnAppId/txnVersion options, or a MERGE).
  • In a Lakeflow Declarative Pipeline: land raw lines (header included, with file_path) in one streaming table, then join header rows to data rows on file_path in a downstream streaming table, with a watermark on an ingestion timestamp to bound the join state.

Fix 2: header lookup on executors, for new files only (mapInPandas)

If the files must be read with header=true, move the lookup off the driver and limit it to each batch's new files. mapInPandas runs the reads in parallel on executors; each reads only the first line.

def first_lines(batches):                         # runs on executors, in parallel
    import fsspec
    for pdf in batches:
        def ts(path):
            with fsspec.open(path, "rb") as f:    # reads only the first block
                return f.readline().decode().strip().split(",")[-1]
        pdf["file_ts_raw"] = pdf["file_path"].map(ts)
        yield pdf

def enrich(batch, batch_id):
    files = batch.select("file_path").distinct()               # this batch's files only
    hdr = files.mapInPandas(first_lines, "file_path string, file_ts_raw string")
    (batch.join(F.broadcast(hdr), "file_path")                 # broadcast hint: fine on serverless too
          .withColumn("file_generated_ts", F.to_timestamp("file_ts_raw", "yyyyMMddHHmmss"))
          .write.mode("append").saveAsTable("bronze.orders"))

The batch is scanned and parsed twice here (once for distinct(), once for the join). On classic compute, batch.persist() avoids that; on serverless, caching isn't available. Only the distinct file paths are shuffled, and the join is a broadcast, so data rows never move.

Check storage access first
On serverless and Unity Catalog shared compute, Python UDF code runs isolated and may not be able to open S3 paths with the workspace's storage credentials the way Spark's own readers can. Confirm fsspec.open works there before relying on this fix.
Does a pandas UDF fix this on its own?
Only partly. pandas UDFs speed up CPU work per row by vectorising it over Arrow batches (Module 2 deep dive). This problem is I/O: one S3 request per file. The gain in Fix 2 comes from running those requests in parallel on executors and only for new files, not from vectorisation, and every file is still read twice. Where a pandas UDF genuinely helps is Fix 3: moving rows cheaply into Python and running per-file logic inside each task, with no extra reads.

Fix 3 (fastest, with a precondition): carry the header forward inside each task

Spark splits a file across tasks only when it's larger than spark.sql.files.maxPartitionBytes (128 MB by default) and splittable. When each file is read by a single task, that task meets the file's header row first, so it can fill in the timestamp itself: one read, no shuffle, no second scan. Read with header=false as in Fix 1.

HEADER_FIRST = "SOURCE_ID"

def fill_file_ts(batches):                         # one call per task; rows arrive in file order
    seen = {}                                      # file_path -> header value, kept across Arrow batches
    for pdf in batches:
        is_hdr = pdf["c0"] == HEADER_FIRST
        seen.update(zip(pdf.loc[is_hdr, "file_path"], pdf.loc[is_hdr, "c_last"]))
        out = pdf.loc[~is_hdr].copy()
        out["file_ts_raw"] = out["file_path"].map(seen)
        if out["file_ts_raw"].isna().any():        # this task never saw the header: the file was split
            raise ValueError("file split across tasks; use Fix 1 or raise maxPartitionBytes")
        yield out.drop(columns=["c_last"])

def enrich(batch, batch_id):
    (batch.mapInPandas(fill_file_ts, out_schema)   # narrow: same partitions, no shuffle
          .withColumn("file_generated_ts", F.to_timestamp("file_ts_raw", "yyyyMMddHHmmss"))
          .write.mode("append").saveAsTable("bronze.orders"))
  • Cost: one S3 read and one parse. Rows do travel JVM → Python → JVM as Arrow batches, but that's an in-memory, vectorised transfer, usually much cheaper than writing and fetching shuffle files.
  • The precondition: no file is split across tasks. Guarantee it by keeping source files under 128 MB (common for feed files), raising maxPartitionBytes above the largest file, or using a format Spark can't split (gzip-compressed CSV, or multiLine=true). Each large file then becomes one big task.
  • The guard fails the batch instead of silently writing nulls if a file ever is split. The failed batch replays from the offset log, so you can fix the setting or switch it to Fix 1 and rerun.
  • Works on serverless: mapInPandas is supported over Spark Connect.

To decide between Fix 1 and Fix 2 on real data, compare the stage's Shuffle Write with its Input size in the Spark UI: a shuffle roughly the size of the input on fast local disks is often cheaper than re-reading and re-parsing it from S3, but measure.

Also

  • Auto Loader discovery: for large, growing locations use file notification mode (or managed file events on newer Databricks runtimes) instead of directory listing.
  • Upstream: ask the source to put the timestamp in the file name or as a column on every row, matching your other sources.

Prevent

  • Review any framework step that loops over files or calls cloud storage from the driver. Per-file metadata should come from the data Spark already reads (_metadata columns, header rows) or be computed on executors.
Say it in an interview (STAR)
"One source put its file timestamp in the CSV header instead of the file name. The first design read every file's header on the driver, built a map and broadcast it, so runtime grew with the bucket's total file count. I changed it to read the header line as a normal row and copy its timestamp to the file's rows within the micro-batch, which works because Auto Loader never splits a file across batches. A window does that with one shuffle; since our files were small and never split across tasks, a mapInPandas pass could do it inside each task with no shuffle at all, guarded to fail if a file ever was split. That removed the second read and the driver bottleneck, and I switched Auto Loader to file notifications so discovery stopped scaling with the bucket too."

Common interview questions

Explain the Spark execution flow from spark-submit to job completion.
The driver starts, creates the SparkSession and gets executors from the cluster manager. Transformations build a logical plan. An action creates a job; Catalyst optimises the plan; the DAG scheduler cuts it into stages at shuffles; the task scheduler sends one task per partition to executor cores; stages run in dependency order, with shuffle files passed between them; results return to the driver, and failed tasks are retried using lineage.
How are jobs, stages and tasks created?
Each action creates a job. The DAG scheduler walks back from the result and creates a new stage at each shuffle dependency. Each stage has one task per partition of its data.
What's lazy evaluation and why does Spark use it?
Transformations only record a plan; work happens when an action needs a result. That lets Catalyst optimise the whole chain, fuse narrow steps into one pass, and recover lost partitions from lineage. It's per action, so each action recomputes its lineage unless cached.
What are narrow and wide transformations, and how do they relate to stages?
Narrow transformations build each output partition from one input partition (filter, select, map), so they're pipelined within a stage. Wide ones need data from many partitions (groupBy, distinct, most joins), so they shuffle, and each shuffle is a stage boundary.
Why are RDDs immutable?
So lineage-based recovery is safe (a recomputed partition equals the original) and parallel tasks need no locking. Every transformation returns a new RDD or DataFrame.
Your job runs much longer than expected and the UI shows the same scan in several jobs. Why?
Several actions are re-running the same lineage. Cache the shared DataFrame, write an intermediate table, or remove debug actions.
