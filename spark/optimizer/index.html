How Spark decides how to run your query

Catalyst rewrites your plan before it runs; AQE rewrites it again while it runs. Knowing both lets you predict what Spark will do and read explain() with confidence. A 10-minute refresher.

Catalyst: four phases

SQL and the DataFrame API compile to the same plan, which is why they perform the same. Catalyst, Spark's query optimiser, turns that plan into running code in four phases.

  1. Analysis. Resolves table and column names against the catalog. A misspelt column fails here with AnalysisException.
  2. Logical optimisation. Rule-based rewrites: push filters down, prune columns, fold constants, combine filters.
  3. Physical planning. Picks concrete operators, for example a broadcast or sort-merge join, using sizes and thresholds.
  4. Code generation. Tungsten fuses each stage's operators into one compiled function working on compact binary rows. On Databricks, Photon replaces much of this with a vectorised C++ engine.

Adaptive Query Execution (AQE)

Catalyst plans with estimates. AQE, on by default since Spark 3.2, re-plans between stages using the real sizes measured at each shuffle. It does three things:

  • Coalesces many small post-shuffle partitions into fewer, right-sized ones.
  • Switches join strategy, for example sort-merge to broadcast, when a side turns out small.
  • Splits skewed partitions in sort-merge joins so one hot key doesn't stall the stage.

It can't fix skew in aggregations or windows, a bad file layout, or slow UDFs. See each rewrite before and after →

UDF cost in one line

Built-in functions (fastest, fully optimised) → pandas UDFs (Arrow batches, vectorised) → plain Python UDFs (row by row, slowest). Catalyst can't look inside any UDF, so it can't push filters through them. The full story is in Module 2's Arrow deep dive.

Say it in an interview

Catalyst
"Catalyst analyses the plan against the catalog, applies rule-based rewrites like predicate pushdown and column pruning, chooses physical operators such as the join strategy, and Tungsten generates compiled code for each stage. SQL and DataFrames go through the same pipeline, so they perform the same."
Join strategies
"If one side is under the broadcast threshold Spark broadcasts it and joins the big side in place, with no shuffle. Otherwise it defaults to sort-merge join, which shuffles and sorts both sides. Shuffle hash join suits a medium build side, and nested-loop joins are only for non-equi conditions."
AQE
"AQE re-optimises at each shuffle using real sizes: it coalesces small partitions, switches sort-merge to broadcast when a side turns out small, and splits skewed join partitions. It doesn't fix skewed aggregations or slow UDFs."

Quick check

Your filter is date(event_ts) = '2026-10-01' and the table is partitioned by event_date. Why is it slow?
It filters on a function of a non-partition column, so there's no partition pruning and weaker pushdown. Filter on event_date, or on an event_ts range.
A 30 MB dimension is joined with a sort-merge join. Two fixes?
Raise autoBroadcastJoinThreshold above 30 MB, or add a broadcast() hint. With AQE on, Spark may switch at runtime once it measures the filtered side.
explain() shows SortMergeJoin but the job ran a broadcast join. How?
AQE changed the plan at runtime. explain() shows the initial plan (isFinalPlan=false); the SQL tab in the Spark UI shows the final one.
Predicate pushdown vs partition pruning?
Partition pruning skips whole folders using partition-column filters. Pushdown sends filters into the file reader to skip row groups inside files that are still read.
Can AQE fix a skewed groupBy?
No. AQE's skew handling covers sort-merge joins. Skewed aggregations need salting or a two-step aggregation.
