Reading a physical plan

Run df.explain("formatted") (or EXPLAIN FORMATTED in SQL). Read it bottom up: scans at the bottom, the result at the top. This is the orders/customers query from the deep dive.

AdaptiveSparkPlan isFinalPlan=false
+- HashAggregate(keys=[segment], functions=[sum(amount)])
   +- Exchange hashpartitioning(segment, 200)
      +- HashAggregate(keys=[segment], functions=[partial_sum(amount)])
         +- Project [amount, segment]
            +- BroadcastHashJoin [cust_id], [cust_id], Inner, BuildRight

               :  +- FileScan parquet [cust_id,amount,country]

               :       ReadSchema: struct<cust_id:bigint,amount:double,country:string>

Look forMeaning
ExchangeA shuffle, and a stage boundary. Count them; each one costs network and disk.
BroadcastHashJoin / SortMergeJoinThe join strategy chosen. A sort-merge join on a small table is a tuning opportunity.
BuildRight / BuildLeftWhich side is hashed (or broadcast)
partial_sum → sumMap-side pre-aggregation before the shuffle
PushedFilters, PartitionFiltersWhether your filters reached the source. Empty lists mean full scans.
AdaptiveSparkPlan isFinalPlan=falseAQE is on; the plan may change at runtime. Check the SQL tab of the Spark UI for the final plan.
*(2) prefixesOperators fused into whole-stage codegen block 2 (plain explain() output)

Join strategy picker

Set the join and the sizes; see what Spark plans before running, and what AQE would switch to once real sizes are known. It follows Spark's main selection rules, simplified.

    Try: set the runtime size above the threshold, switch to FULL OUTER, or add BROADCAST(left) to a LEFT OUTER join. A threshold of -1 disables automatic broadcasting.

    Join hints

    from pyspark.sql.functions import broadcast

orders.join(broadcast(customers), "cust_id")                 # force broadcast of customers
orders.hint("merge").join(customers, "cust_id")              # ask for sort-merge
orders.join(customers.hint("shuffle_hash"), "cust_id")       # ask for shuffle hash

spark.sql("""
  SELECT /*+ BROADCAST(c) */ o.*, c.segment
  FROM orders o JOIN customers c USING (cust_id)
""")
# SQL hints: BROADCAST (also BROADCASTJOIN, MAPJOIN), MERGE, SHUFFLE_HASH, SHUFFLE_REPLICATE_NL
    Hints are commands, not suggestions
    A BROADCAST hint broadcasts the table even if it's far over the threshold, which is how many driver OOMs start. Use hints for stable, known-small tables, and prefer fixing statistics or thresholds so Spark chooses correctly on its own.

    Check yourself

    Why can't Spark broadcast the left side of a LEFT OUTER join?
    Every left row must appear in the output, matched or not. If the left side were broadcast, each executor would see all left rows but only part of the right side, and couldn't tell whether a left row matched somewhere else. So only the right side (the non-preserved side) can be the build side.
    Which strategies can handle a FULL OUTER equi-join?
    Sort-merge join (the default), and shuffle hash join since Spark 3.1. Broadcast hash join can't, because both sides are preserved.
    The plan says SortMergeJoin, the job ran a BroadcastHashJoin. Which setting made that possible?
    spark.sql.adaptive.enabled: AQE measured the real size of one side after its stage ran, found it under the (adaptive) broadcast threshold, and switched strategy.
    What does spark.sql.autoBroadcastJoinThreshold = -1 do?
    Disables automatic broadcast joins. Explicit BROADCAST hints still work.
