Statistics and the cost-based optimiser

    
Physical planning needs sizes: is this table small enough to broadcast? Spark gets them from statistics.

    
    
      
  • Without collected statistics, Spark estimates size from file sizes on disk. That's fine for raw scans, but after filters and joins estimates can be far off. Compressed files also expand several times in memory.
    • 
      
  • Table and column statistics (ANALYZE TABLE t COMPUTE STATISTICS FOR ALL COLUMNS) record row counts, distinct values, min/max and null counts. Delta tables keep file-level statistics automatically.
    • 
      
  • The cost-based optimiser (spark.sql.cbo.enabled, off by default) uses column statistics to estimate filter selectivity and, with spark.sql.cbo.joinReorder.enabled, to reorder multi-way joins so the most selective joins run first.
    • 
      
  • AQE sidesteps much of this: it measures real shuffle sizes at runtime and corrects the plan between stages, which is why it's on by default and CBO isn't.
    • 
    

    
Stale statistics are worse than none
If a table grew 100× since it was analysed, Spark may still think it's small and broadcast it, causing driver OOM or broadcast timeouts. Re-analyse after big loads, or rely on AQE and sensible thresholds.

Dynamic partition pruning

    
Static partition pruning needs a filter on the partition column itself. Often the filter is on a dimension instead:


SELECT f.*
FROM sales f                       -- partitioned by date_key
JOIN dim_date d ON f.date_key = d.date_key
WHERE d.fiscal_quarter = 'FY26-Q2'

    
Nothing filters sales.date_key directly, so static pruning reads every partition. With dynamic partition pruning (Spark 3.0+, on by default), Spark first runs the filtered dimension side, collects the matching date_key values, and injects them as a partition filter on sales at runtime, so only those partitions are read. It works best when the dimension side is small enough to broadcast. You'll see dynamicpruningexpression in the scan's PartitionFilters.

What AQE can't fix
Skew in a groupBy aggregation or window function (skew handling covers joins only), the very first scan stage (there are no statistics yet), a bad file layout, or a slow Python UDF. Those still need salting, repartitioning or redesign.


  

    
Whole-stage codegen and Photon

    
After physical planning, Tungsten whole-stage code generation fuses all operators between two exchanges into a single Java function, then compiles it. Instead of each operator calling the next for every row, one tight loop handles a row from scan to output. In plain explain() output these operators are prefixed *(n), where n is the codegen block.

    
Some operators can't be fused, for example Python UDFs and some complex expressions, so they break the block and fall back to slower row-by-row evaluation. On Databricks, Photon takes a different approach: a vectorised C++ engine that processes column batches (see three meanings of "vectorised").

  


  

    
Check yourself

    

      
In which Catalyst phase is a misspelt column caught, and in which is the join strategy chosen?
A misspelt column fails in analysis. The join strategy is chosen in physical planning, and AQE may change it again at runtime.

      
Why does upper(country) = 'AE' read every row group?
Row-group statistics are min/max of the raw country values. Spark can't map a condition on upper(country) back to those ranges, so nothing can be skipped. Store a normalised column, or filter on raw values.

      
When does dynamic partition pruning help?
When a large fact table partitioned by a key is joined to a dimension, and the filter is on the dimension rather than on the fact's partition column. The filtered dimension's keys prune the fact's partitions at runtime.

      
Why is AQE on by default but the cost-based optimiser isn't?
CBO depends on accurate, up-to-date column statistics, which many tables don't have. AQE uses real sizes measured during execution, so it works without any preparation.
