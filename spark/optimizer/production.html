When the optimiser gets it wrong

Catalyst and AQE make good choices from what they can see. These problems happen when they can't see enough: hidden columns, stale sizes, missing join keys. Each follows the same path: symptom, why, how to confirm, fix, prevention, interview answer.

Filters not pushed down

Symptom

A query with a selective filter still reads the whole table: the scan's input size in the SQL tab equals the table size, and PushedFilters or PartitionFilters are empty in explain().

Why it happens

  • The column is wrapped in a function: to_date(ts) = …, upper(country) = …, substr(id, 1, 3) = ….
  • The filter uses a Python UDF's output, which Catalyst can't see into.
  • The filter is applied after an operation that blocks pushdown, such as some window functions, or a DataFrame → RDD round-trip.
  • The source has no statistics (CSV, JSON) or the data is so mixed that min/max ranges cover everything.

How to confirm

  1. df.explain("formatted"): check the scan's PushedFilters and PartitionFilters.
  2. SQL tab: compare "files read" and "size of files read" with the table size.

Fix

  • Rewrite filters on raw columns: ts >= '2026-10-01' AND ts < '2026-10-02' instead of to_date(ts) = '2026-10-01'.
  • Store normalised or derived columns (for example a country_upper or event_date column) and filter on those.
  • Filter as early as possible, before UDFs and windows.
  • Improve layout so statistics are useful: partition by date, cluster (ZORDER / liquid clustering) by common filter columns.
Say it in an interview
"I check PushedFilters and PartitionFilters in explain. If they're empty, it's usually a function or UDF wrapped around the column, so I rewrite the filter as a range on the raw column or add a derived column, and make sure data is laid out so min/max statistics can actually skip files."

Filtering on a column the table isn't partitioned by

Symptom

A table partitioned by event_date is queried with WHERE event_ts >= '2026-10-01 00:00' AND event_ts < '2026-10-02 00:00', and every partition is listed and scanned. PartitionFilters is empty.

Why it happens

Spark prunes partitions only from filters on the partition column itself. It doesn't know that event_date is derived from event_ts, so a filter on the timestamp can't skip any event_date=… folder. Pushdown on event_ts may still skip some row groups inside files, but every folder is opened.

How to confirm

  1. explain("formatted"): PartitionFilters is empty while PushedFilters mentions event_ts.
  2. SQL tab: number of files read equals the table's file count.

Fix

  • Add the partition filter explicitly: event_date = '2026-10-01' alongside the timestamp range.
  • On Delta, declare the partition column as a generated column (GENERATED ALWAYS AS (CAST(event_ts AS DATE))); Delta can then derive the partition filter from the timestamp filter automatically.
  • Document the partition column for table users, and make it the natural one to filter on.
Say it in an interview
"Partition pruning only works when you filter on the partition column itself. If a table is partitioned by date and people filter on the timestamp, every partition is scanned. I add the date filter explicitly, or use Delta generated columns so the partition filter is derived automatically."

Wrong join strategy from bad size estimates

Symptom

Either a tiny table is joined with a sort-merge join (two shuffles of a huge table), or a large table is broadcast and the job hits driver OOM or a broadcast timeout.

Why it happens

  • Missing or stale statistics: Spark estimates a filtered table from its full file size, or thinks a table is small because it was analysed long ago.
  • Compressed file size isn't memory size: Parquet commonly expands several times when decoded.
  • The threshold was raised cluster-wide, or a broadcast() hint sits on a table that grew.

How to confirm

  1. Compare the strategy in explain() with the final plan in the SQL tab (AQE may already have corrected it).
  2. Check the real sizes of both join inputs in the SQL tab.
  3. DESCRIBE EXTENDED / DESCRIBE DETAIL to see the statistics Spark has.

Fix

  • Keep AQE on so it can switch to broadcast at runtime.
  • Refresh statistics after large loads (ANALYZE TABLE … COMPUTE STATISTICS).
  • Set the threshold per job to what your executors can hold, rather than raising it cluster-wide.
  • Remove broadcast hints from tables that aren't reliably small.

Broadcast memory failures in detail: Module 1 · Broadcast too big. Try scenarios in the join strategy picker.

Say it in an interview
"Join choice depends on size estimates. With stale or missing statistics Spark can shuffle a tiny table or broadcast a huge one. I keep AQE on, refresh statistics after big loads, tune the threshold per job, and use hints only for tables I know stay small."

Accidental cartesian join

Symptom

A join step outputs billions of rows, runs for hours or never finishes. The plan shows CartesianProduct or BroadcastNestedLoopJoin.

Why it happens

  • The join condition is missing or wrong (joining on a column that is constant or NULL).
  • The condition is non-equi only (a.ts BETWEEN b.start AND b.end), so no hash or sort-merge join is possible.
  • An OR across columns (a.id = b.id OR a.email = b.email) can stop Spark from using an equi-join.

How to confirm

  1. Look for CartesianProduct / BroadcastNestedLoopJoin in the plan.
  2. SQL tab: rows output from the join node are far larger than either input.

Fix

  • Add the missing equality key. For range joins, add an equality "bucket" key too (for example join on the date, then filter the time range) so Spark can use a hash or sort-merge join.
  • Split OR joins into two equi-joins and union the results.
  • Make cross joins explicit with crossJoin() only when you really mean them.
Say it in an interview
"If a join explodes, I check the plan for a cartesian product or nested-loop join, which means there's no usable equality condition. I add an equality key, bucket range joins on something like the date first, and split OR conditions into separate equi-joins."

AQE isn't helping

Symptom

You expected AQE to coalesce partitions or fix skew, but the job still has 200 tiny tasks or one huge straggler.

Why it happens

  • AQE is disabled, or the platform version predates it being on by default (before Spark 3.2).
  • There's no shuffle in that part of the query; AQE only re-plans at shuffle boundaries.
  • The skew is in an aggregation or window, not a sort-merge join.
  • The skewed partition is below the thresholds (5 × median and 256 MB).
  • The problem is in the first scan stage, before any statistics exist.

Fix

  • Confirm spark.sql.adaptive.enabled=true and look for AdaptiveSparkPlan in the plan.
  • Tune the advisory partition size and skew thresholds for your data.
  • For skewed aggregations: salting or a two-step aggregation (Module 5 · Data skew).
Say it in an interview
"AQE only acts at shuffle boundaries, and its skew handling covers sort-merge joins. If it isn't helping, I check it's enabled, check the skew thresholds, and handle aggregation skew myself with salting."

Broadcast timeout

Symptom

Could not execute broadcast in 300 secs. You can increase the timeout for
broadcasts via spark.sql.broadcastTimeout or disable broadcast join by setting
spark.sql.autoBroadcastJoinThreshold to -1

Why it happens

The side being broadcast is expensive to compute (a big upstream join or aggregation), or large to collect and send, so building the broadcast takes longer than 300 seconds.

Fix

  • If the side is genuinely small but slow to compute, materialise it first (cache or write it), then broadcast the result; or raise spark.sql.broadcastTimeout.
  • If it's genuinely big, stop broadcasting it: remove the hint or lower the threshold.
Say it in an interview
"A broadcast timeout means building the broadcast side took over five minutes, either because it's expensive to compute or too big. I materialise the small side first, or stop broadcasting it if it's actually large."

Plan regressions after an upgrade or config change

Symptom

A stable job becomes much slower after a Spark/runtime upgrade, a config change, or a schema change, with no code change.

Why it happens

New versions change optimiser rules and defaults; a schema change can alter types or statistics; a config change (threshold, AQE settings) changes join or partition choices.

How to confirm

  1. Compare explain("formatted") output and the SQL-tab plans from before and after: join strategies, number of Exchanges, pushed filters.

Fix and prevent

  • Pin the problematic choice with a hint or a targeted config while investigating.
  • Keep a "golden" plan for critical jobs and diff it in testing before upgrades.
Say it in an interview
"When a job regresses without a code change, I diff the physical plans before and after. Usually a join strategy or a lost pushdown explains it. For critical jobs I keep reference plans and compare them when upgrading."

Common interview questions

Explain the Catalyst optimiser.
It turns a query into an unresolved logical plan, resolves it against the catalog (analysis), applies rule-based optimisations like predicate pushdown, column pruning and constant folding, picks physical operators such as join strategies using sizes and thresholds, then Tungsten generates compiled code for each stage.
What is predicate pushdown?
Passing filter conditions down to the data source so it can skip data before Spark reads it. With Parquet, the reader uses per-row-group min/max statistics to skip row groups that can't match.
Partition pruning vs dynamic partition pruning?
Static pruning uses filters on the partition column itself to skip folders at planning time. Dynamic pruning uses the filtered keys of another (dimension) table at runtime to prune the fact table's partitions in a join.
How does Spark choose a join strategy?
Hints first; then broadcast hash join if a buildable side is under the broadcast threshold; otherwise sort-merge join by default, or shuffle hash join when preferred and suitable. Non-equi joins use nested-loop strategies. AQE can switch to broadcast at runtime when a side turns out small.
What is AQE and what does it optimise?
Adaptive Query Execution re-plans between stages using real shuffle statistics: it coalesces small partitions, switches sort-merge joins to broadcast joins, and splits skewed partitions in sort-merge joins.
Why would explain() show a different plan from what ran?
With AQE on, explain() shows the initial plan. AQE can change join strategies and partition counts during execution; the SQL tab shows the final plan.
