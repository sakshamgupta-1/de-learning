Arrow and vectorised execution

Why pandas UDFs are so much faster than plain Python UDFs, what Apache Arrow actually does, and the three different things people mean by "vectorised" in Spark.

Row layout vs columnar layout

The same three-row table can sit in memory two ways. Row layout keeps each record together, which suits reading or writing whole records. Columnar layout keeps each column together, which suits analytics: most queries touch a few columns of many rows.

Highlights the values each layout has to read to add up amount.
  • Fewer bytes read: a query on amount touches only the amount block.
  • CPU-friendly: values of one type sit next to each other, so the CPU cache is used well and one instruction can process several values at once.
  • Better compression: similar values side by side compress well. That's why Parquet and ORC files are columnar.

What Apache Arrow is

Apache Arrow is a standard columnar format for data in memory, defined the same way for every language. A batch of Arrow data (a record batch) is a set of column buffers plus a schema. Because Java, Python, C++ and others all understand the same layout, they can hand data to each other without converting it value by value, often without copying it at all.

Parquet is columnar on disk; Arrow is columnar in memory. pandas and NumPy are columnar in memory too, which is why converting Arrow to pandas is cheap.

Crossing the JVM ↔ Python boundary

Spark's engine runs in the JVM; your Python function runs in separate Python worker processes on each executor. Every Python UDF means moving data across that process boundary and back. How it's moved makes the difference.

Batches of rows are buffered in the Python worker's memory, which counts against the executor's overhead, not its heap. If pandas UDF stages get containers killed, lower the batch size or raise overhead (see Module 1).

What "vectorised" means

Vectorised code applies one operation to a whole array of values at once, instead of looping over values one at a time in an interpreted language. In pandas and NumPy, s * 1.05 runs a single loop in compiled C over the whole column, often using CPU instructions that process several numbers per step (SIMD). A plain Python function pays the interpreter's overhead on every single value.

import pandas as pd
from pyspark.sql import functions as F
from pyspark.sql.functions import udf, pandas_udf

@udf("double")
def tax_row(amount):                       # called once per row, in the Python interpreter
    return amount * 1.05

@pandas_udf("double")
def tax_vec(amount: pd.Series) -> pd.Series:   # called once per batch of ~10,000 rows
    return amount * 1.05                   # one compiled loop over the whole array

df.withColumn("t", tax_row("amount"))      # slowest: pickle + interpreter per row
df.withColumn("t", tax_vec("amount"))      # much faster: Arrow + vectorised NumPy
df.withColumn("t", F.col("amount") * 1.05) # fastest: no Python at all
A pandas UDF isn't automatically vectorised
If your pandas UDF does s.apply(lambda x: …) or loops over rows in Python, you get Arrow's cheaper transfer but still pay the interpreter per value. The big win needs whole-column pandas or NumPy operations inside the function.

For contrast, open-source Spark's Tungsten whole-stage codegen fuses the operators of a stage into one compiled Java function that processes one row at a time in a tight loop. It's fast because it removes per-operator overhead, but it's row-oriented, not vectorised. That's the main design difference Photon changes.

Say it in an interview

Why pandas UDFs beat Python UDFs
"A plain Python UDF pickles every row, sends it to a Python worker and calls the function once per row in the interpreter. A pandas UDF ships Arrow record batches of about ten thousand rows, so there's no per-row conversion, and the function runs once per batch on whole pandas Series, which NumPy processes in compiled, vectorised loops."
What Arrow is
"Apache Arrow is a language-neutral columnar in-memory format. Because the JVM and Python agree on the layout, Spark can hand column buffers to pandas without converting each value. Spark uses it for toPandas, createDataFrame from pandas, and all pandas UDFs."
"Vectorised" in Spark
"It can mean pandas UDFs running NumPy over Arrow batches, the vectorised Parquet reader decoding column batches, or Photon, Databricks' C++ engine that processes whole column batches. Open-source Spark's whole-stage codegen is compiled but processes one row at a time."

Quick check

Does setting arrow.pyspark.enabled=false make pandas UDFs stop using Arrow?
No. pandas UDFs, mapInPandas and applyInPandas always use Arrow. That setting only affects toPandas() and createDataFrame from a pandas DataFrame.
Your pandas UDF calls s.apply(my_func). Is it vectorised?
Only the transfer is. apply calls a Python function per value, so you still pay interpreter overhead per row. Rewrite with whole-Series operations (arithmetic, np.where, .str methods) to get the real speed-up.
A pandas UDF stage keeps getting containers killed. Which Arrow setting can help?
spark.sql.execution.arrow.maxRecordsPerBatch: smaller batches mean less Python-worker memory per task. Raising executor memory overhead also helps.
Why is Arrow → pandas conversion cheap but pickle → pandas expensive?
Arrow and pandas are both columnar, so pandas can wrap Arrow's column buffers, often without copying. Pickled rows must be decoded one Python object at a time and reassembled into columns.
