Crossing between Spark and pandas

Most problems in this area happen where data moves between worlds: Spark to pandas, JVM to Python, DataFrame to RDD. Each issue below follows the same path: symptom, why, how to confirm, fix, prevention, interview answer.

toPandas() runs the driver out of memory

Symptom

java.lang.OutOfMemoryError: Java heap space          (driver)
Total size of serialized results of 512 tasks (1024.0 MiB)
is bigger than spark.driver.maxResultSize (1024.0 MiB)

Or the notebook hangs for minutes and then the Python process is killed.

Why it happens

  • toPandas() is an action, evaluated immediately. When Python reaches that line it blocks: Spark runs the whole lineage as a job (re-reading the source unless it's cached), pulls every row to the driver, and builds a pandas DataFrame there before the next line runs.
  • Data exists in the JVM, in transit and in pandas at the same moment, so peak memory is a multiple of the data size.
  • After the call it's plain, eager pandas: no lineage, no laziness, no link back to the Spark DataFrame.
  • It's often called "just to look" at a table, or on data that was small in development and grew in production.

How to confirm

  1. The failure is in the driver log, right after the toPandas call.
  2. Check the result size first: df.count() and the number of columns.

Fix

  • Aggregate or filter in Spark first; convert only the small result.
  • For a look at the data, use df.limit(1000).toPandas() or df.show().
  • For handing data to another system, write it to a table or files instead.
  • Enable Arrow (spark.sql.execution.arrow.pyspark.enabled=true). It cuts conversion time and overhead, but every row still lands on the driver.

Safer alternatives

CallLazy or eagerWhat reaches the driver
df.toPandas()Eager (action)Every row, as one pandas DataFrame
df.limit(1000).toPandas()Eager (action)Only 1,000 rows; usually reads just part of the data
df.toLocalIterator()Eager, one partition at a time as you iterateAbout one partition in memory at a time
df.pandas_api()LazyNothing: a pandas-style API over distributed data
df.write…Eager (action)Nothing: executors write the data directly

Prevent

  • Team rule: toPandas() only after an aggregation or a limit, never on raw tables.
Say it in an interview
"toPandas collects the whole DataFrame to the driver and builds a pandas copy, so it's a driver OOM waiting to happen on large data. I reduce the data in Spark first, convert only small results with Arrow enabled, and write anything big to storage instead."

Arrow silently falls back to the slow path

Symptom

UserWarning: toPandas attempted Arrow optimization because
'spark.sql.execution.arrow.pyspark.enabled' is set to true; however,
failed by the reason below: ...
Attempting non-optimization as
'spark.sql.execution.arrow.pyspark.fallback.enabled' is set to true.

The conversion still works, just many times slower, and the warning is easy to miss in a job log.

Why it happens

  • A column type Arrow can't convert in your Spark version (some nested or complex types), or a version mismatch between PySpark, PyArrow and pandas.
  • Fallback is on by default, so Spark quietly switches to row-by-row conversion instead of failing.

How to confirm

  1. Search driver logs for attempted Arrow optimization.
  2. Re-run with fallback disabled to see the real error: 
    spark.conf.set("spark.sql.execution.arrow.pyspark.fallback.enabled", "false")

Fix

  • Cast or flatten the unsupported column (for example to_json on a complex struct) before converting.
  • Align PyArrow and pandas with the versions your Spark release supports.

Prevent

  • Disable fallback in tests and CI so incompatibilities fail loudly there instead of slowing production.
Say it in an interview
"Arrow makes Spark-to-pandas conversion columnar and fast, but by default Spark falls back silently when Arrow can't handle a type. I turn fallback off in testing so those cases fail visibly, then fix the column types."

Slow Python UDFs

Symptom

No error; the job is just slow. The stage running the UDF dominates the runtime, executor CPU sits in Python processes, and the plan shows a BatchEvalPython node (plain Python UDF) or ArrowEvalPython (pandas UDF).

Why it happens

  • A plain Python UDF processes one row at a time: each row is serialised in the JVM, sent to a Python worker, processed and sent back.
  • Catalyst can't see inside the UDF, so filters that depend on its output can't be pushed down.
  • Python workers also use memory outside the JVM heap, which can lead to "container killed" errors (see Module 1).

How to confirm

  1. df.explain() shows BatchEvalPython.
  2. Compare stage time with the UDF replaced by a no-op or built-in.

Fix

  • Rewrite with built-in functions where possible: the biggest win.
  • Otherwise use a pandas UDF: Arrow batches and vectorised pandas or NumPy code (why it's faster).
  • If the slow part is I/O per item (opening files, calling APIs) rather than CPU, vectorising won't help much; parallelise it on executors and avoid repeat reads. Real example: reading per-file header values.
  • On Spark 3.5+, an Arrow-optimised Python UDF (@udf(useArrow=True)) keeps row-wise code but speeds up data transfer.
  • Apply UDFs after filtering, so fewer rows reach Python.
# before: row-at-a-time Python UDF
@udf("string")
def tier(amount): return "high" if amount > 1000 else "low"

# after: built-in, stays in the JVM and is optimised
df.withColumn("tier", F.when(F.col("amount") > 1000, "high").otherwise("low"))
Say it in an interview
"Plain Python UDFs serialise every row to Python and back, and they're opaque to Catalyst. I replace them with built-ins first; if I really need Python, I use pandas UDFs for vectorised Arrow batches, and I filter before the UDF so less data crosses into Python."

Losing optimisation with DataFrame → RDD → DataFrame

Symptom

A pipeline that does df.rdd.map(…).toDF() in the middle is much slower than expected, reads far more data than its inputs suggest, and its plan shows full scans with no PushedFilters.

Why it happens

  • Catalyst optimises up to the .rdd call and after the toDF(), but can't optimise across it. Filters later in the pipeline can't be pushed back into the scan.
  • Rows are converted from Tungsten's binary format into Python Row objects and back.
  • toDF() without a schema samples rows to infer types: an extra job, and sometimes the wrong types.

Fix

  • Express the logic with built-ins, a pandas UDF or mapInPandas (see Examples).
  • If an RDD step truly can't be avoided, filter and select columns before .rdd, and pass an explicit schema to createDataFrame.
Say it in an interview
"Dropping to an RDD creates an optimisation barrier: Catalyst can't push filters or prune columns across it, and every row is converted to Python objects. I keep pipelines in DataFrames and use pandas UDFs or mapInPandas for custom logic."

pandas API on Spark surprises

Symptom

ValueError: Cannot combine the series or dataframe because it comes from
a different dataframe. In order to allow this operation, enable
'compute.ops_on_diff_frames' option.

Or code that was instant in pandas runs very slowly, or a step quietly moves all data into one partition.

Why it happens

  • The index is expensive. pandas assumes a row order and index; Spark has neither natively. Creating a sequential default index, or aligning two DataFrames by index, needs extra passes or joins.
  • Combining two different DataFrames requires a join on the index, which is disabled by default because it's costly.
  • Some operations don't distribute well: anything needing a global row order, or positional access like iloc on big data.

Fix

  • Set index_col when reading or converting, or use compute.default_index_type = "distributed" when consecutive index values don't matter.
  • Join explicitly on a key column instead of relying on index alignment; enable compute.ops_on_diff_frames only when you accept the cost.
  • Switch to the Spark DataFrame API (psdf.to_spark()) for heavy steps.
Say it in an interview
"The pandas API on Spark gives pandas syntax on distributed data, but pandas assumes an ordered index, which is expensive to provide at scale. I set an index column, avoid combining different frames by index, and switch to the DataFrame API for heavy transformations."

RDD code fails on Spark Connect and serverless

Symptom

[JVM_ATTRIBUTE_NOT_SUPPORTED] Attribute `sparkContext` is not supported
in Spark Connect as it depends on the JVM.

[NOT_IMPLEMENTED] rdd() is not implemented.

Exact messages vary by Spark and Databricks version.

Why it happens

With Spark Connect (Spark 3.4+), your Python code is a thin client that sends unresolved plans to a remote Spark server. There's no JVM in your process, so JVM-bound APIs such as sparkContext, RDDs and df.rdd aren't available. Databricks serverless and shared-access compute work this way.

Fix

  • Rewrite RDD logic with DataFrame operations, built-ins, pandas UDFs or mapInPandas.
  • Replace sc.broadcast with broadcast joins, sc.parallelize with spark.createDataFrame, and accumulators with aggregations.

Prevent

  • Treat RDD usage as technical debt in new code, and flag it in code review.
Say it in an interview
"Spark Connect separates the client from the Spark driver, so APIs that need the JVM, like sparkContext and RDDs, don't exist on the client. That's how Databricks serverless works, so I write new code purely against the DataFrame API."

Common interview questions

Compare RDD, DataFrame and Dataset.
RDD: distributed objects with arbitrary functions, no schema, no optimiser. DataFrame: named, typed columns, optimised by Catalyst and stored compactly by Tungsten; available in all languages. Dataset: the typed JVM version with compile-time checks; a DataFrame is Dataset[Row]. Default to DataFrames; Datasets suit typed Scala code; RDDs only for low-level needs.
Why are DataFrames faster than RDDs, especially in PySpark?
Catalyst understands the query, so it pushes down filters, prunes columns and picks join strategies; Tungsten uses compact binary rows and generated code. In PySpark, RDD lambdas also pickle every row to Python workers and back, while DataFrame operations stay in the JVM.
When would you still use an RDD?
Unstructured data needing custom parsing, low-level partitioning control, or legacy code. Even then, pandas UDFs or mapInPandas often do the job better, and RDDs don't work on Spark Connect.
What's the difference between a Spark DataFrame and a pandas DataFrame?
Spark: distributed, lazy, immutable, no index, scales to any size. pandas: single machine, eager, mutable, indexed, limited by one machine's memory.
Is toPandas() lazy or eager? Does Python wait for it?
Eager: it's an action. When Python reaches the line, Spark runs the lineage as a job, collects every row to the driver and builds the pandas DataFrame; Python waits for all of that before the next line. Upstream errors surface on this line. Afterwards the result is plain eager pandas with no link to the Spark plan, and calling another action on the original DataFrame recomputes it unless it's cached.
What happens when you call toPandas()?
Spark runs the plan, collects every row to the driver, and builds a pandas DataFrame there. With Arrow enabled the transfer is columnar and much faster, but the full data still has to fit in driver memory.
What is Apache Arrow and why does Spark use it?
A columnar in-memory format shared by the JVM and Python. Spark uses it to move data between them in batches without per-row serialisation: in toPandas, createDataFrame from pandas, and pandas UDFs.
pandas UDF vs pandas API on Spark: what's the difference?
A pandas UDF runs your own pandas function on executors over batches or groups of a Spark DataFrame. The pandas API on Spark is a pandas-compatible interface whose calls are translated into Spark plans; you don't write per-batch functions at all.
Are Spark DataFrames mutable?
No. Every transformation returns a new DataFrame with a longer plan; the original is unchanged. Even the pandas API on Spark, which looks mutable, creates new plans underneath.
