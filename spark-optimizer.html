How Spark decides how to run your query

Catalyst rewrites your plan before it runs; AQE rewrites it again while it runs. Knowing both lets you read explain() and predict what Spark will do.

Catalyst: four phases

SQL and the DataFrame API compile to the same plan, which is why they perform the same. Catalyst turns that plan into executable code in four phases.

  1. Analysis. Resolves table and column names and types against the catalog. A misspelt column fails here with AnalysisException, before any job runs.
  2. Logical optimisation. Rule-based rewrites that don't depend on the engine: pushdown, pruning, constant folding, combining filters, simplifying expressions.
  3. Physical planning. Chooses concrete operators, e.g. broadcast hash join vs sort-merge join, using statistics and thresholds.
  4. Code generation. Tungsten fuses operators in a stage into one Java function (whole-stage codegen, shown as *(n) in plans), works on compact binary rows in off-heap memory, and avoids JVM object overhead.

On Databricks, Photon replaces much of step 4 with a vectorised C++ engine. The plan logic is the same; operators show up as Photon… in the plan.

What breaks pushdown

      
    
        
  • Wrapping the column in a function or cast: WHERE to_date(ts) = '2026-10-01' or upper(country) = 'AE'. Filter on the raw column with a range instead.
    • 
        
  • Python UDFs in the filter: Spark can't see inside them.
    • 
        
  • Formats without statistics (CSV, JSON).
    • 
        
  • Badly clustered data: if every file contains every value, min/max stats can't skip anything. That's what ZORDER and liquid clustering fix.

Join strategies

    
For an equi-join, Spark picks roughly in this order: join hint → broadcast if a side is small enough → sort-merge join (default for two large tables) → shuffle hash join when enabled and suitable. Non-equi joins fall back to nested-loop strategies.

    

      
StrategyHow it worksUse whenWatch out

      
        
Broadcast hash joinSmall side collected to driver, sent to every executor, hashed; big side joined in placeOne side < spark.sql.autoBroadcastJoinThreshold (10 MB default; often raised to 50–200 MB)Broadcasting something too large → driver/executor OOM. Can't broadcast the preserved side of an outer join (e.g. the left side of a LEFT JOIN).

        
Sort-merge joinShuffle both sides by key, sort, mergeTwo large tables; scales to any sizeTwo shuffles plus sorts; very sensitive to skew

        
Shuffle hash joinShuffle both sides, build hash table on the smaller side per partitionOne side medium-sized, partitions fit in memoryOOM if a partition's build side doesn't fit

        
Broadcast nested loop / cartesianCompare every pairNon-equi joins (a.ts BETWEEN b.start AND b.end)Quadratic; avoid on large inputs

      


from pyspark.sql.functions import broadcast
orders.join(broadcast(customers), "cust_id")         # force broadcast
spark.sql("SELECT /*+ BROADCAST(c) */ * FROM orders o JOIN customers c USING (cust_id)")
# other hints: MERGE (sort-merge), SHUFFLE_HASH, SHUFFLE_REPLICATE_NL

What AQE can't fix
Skew in a groupBy aggregation or window function (skew-join handling covers joins only), skew in the very first scan stage, a bad file layout, or a Python UDF bottleneck. Those still need salting, repartitioning or redesign.

Say it in an interview

  "Catalyst analyses the plan against the catalog, applies rule-based rewrites like predicate pushdown and column pruning, picks physical operators such as the join strategy by cost, then generates code with Tungsten. AQE then re-optimises at each shuffle using real sizes: it coalesces small partitions, switches sort-merge to broadcast when a side turns out small, and splits skewed join partitions."


  

    
Check yourself

    

      
Your filter is on date(event_ts) = '2026-10-01' and the table is partitioned by event_date. Why is it slow?
The filter is on a function of a non-partition column, so partition pruning doesn't happen and pushdown is weakened. Filter on event_date = '2026-10-01', or on an event_ts range.

      
A 30 MB dimension is joined with a sort-merge join. Two ways to fix it?
Raise autoBroadcastJoinThreshold above 30 MB, or add a broadcast() hint. With AQE on, Spark may also switch at runtime once it measures the filtered side.

      
Why can explain() show SortMergeJoin but the job actually ran a broadcast join?
AQE. explain() shows the initial plan (isFinalPlan=false); AQE changed it at runtime. Check the SQL / DataFrame tab in the Spark UI for the final plan.

      
Difference between predicate pushdown and partition pruning?
Partition pruning skips whole directories based on partition-column filters. Pushdown sends filters into the file reader to skip row groups inside the files that are still read, using column statistics.

      
Why are SQL and DataFrame code equally fast?
Both produce the same unresolved logical plan and go through the same Catalyst pipeline.
