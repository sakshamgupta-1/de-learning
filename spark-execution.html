spark-submit to job completion

  1. Submit. spark-submit (or a Databricks job) starts the driver with your code and config.
  2. Driver starts. Creates the SparkSession and asks the cluster manager for executors.
  3. Executors launch and register with the driver.
  4. Code runs on the driver. Each transformation only adds a step to a logical plan. No data moves.
  5. An action is called (write, count, collect, show). Spark creates a job.
  6. Catalyst optimises the logical plan and picks a physical plan (Module 3).
  7. DAG scheduler cuts the physical plan into stages at every shuffle and submits them in dependency order.
  8. Task scheduler sends one task per partition to free executor cores, preferring data locality.
  9. Executors run tasks. A stage ending in a shuffle writes shuffle files locally; the next stage reads them over the network.
  10. Job finishes when the last stage completes. Failed tasks are retried (default 4 attempts) using lineage. The application ends when the SparkSession stops.

Why Spark is lazy

  • Whole-plan optimisation. Seeing the full chain lets Catalyst push the country = 'AE' filter into the file scan and read only the needed columns.
  • Fewer passes. Consecutive narrow steps are fused into one stage, so data is read once.
  • Fault tolerance through lineage. The plan is a recipe. If an executor dies, Spark recomputes only the lost partitions from the recipe.

RDD immutability and lineage

An RDD (and the DataFrame built on it) is an immutable, partitioned collection plus the lineage of transformations that produced it. Every transformation returns a new dataset. Immutability is what makes recomputation safe: a lost partition rebuilt from lineage is guaranteed to equal the original, and tasks can run in parallel without locks.

Common trap
Every action re-runs the whole lineage. Calling df.count() and then df.write... on an expensive DataFrame reads and computes everything twice. Cache it, or restructure so you need one action.

Narrow vs wide transformations

The single most important distinction in Spark performance. A narrow transformation computes each output partition from one input partition. A wide transformation needs rows from many partitions, so data must be shuffled across the network, and that creates a stage boundary.

select, filter/where, withColumn, map, flatMap, mapPartitions, union, coalesce, sample, explode groupBy/agg, distinct, dropDuplicates, orderBy/sort, repartition, sort-merge join, window functions with partitionBy, reduceByKey join is narrow on the large side when the other side is broadcast, or when both sides are already partitioned the same way (bucketing)

map vs flatMap

rdd = sc.parallelize(["spark is fast", "delta lake"])
rdd.map(lambda s: s.split(" ")).collect()
# [['spark','is','fast'], ['delta','lake']]   one output per input
rdd.flatMap(lambda s: s.split(" ")).collect()
# ['spark','is','fast','delta','lake']         zero or more outputs, flattened

DataFrame equivalent of flatMap: F.explode(F.split("text", " ")).

Jobs, stages and tasks for our pipeline

  • Jobs: one per action. Some actions create extra small jobs (schema inference, file listing, a broadcast build).
  • Stages: Spark walks back from the final operation; every wide dependency (Exchange) starts a new stage. Stages with no dependency on each other can run in parallel.
  • Tasks: one per partition of that stage. Scan stages get one task per file split (~128 MB by default); post-shuffle stages get spark.sql.shuffle.partitions (default 200), unless AQE coalesces them.

One action → one job → four stages. If customers is under the broadcast threshold (10 MB by default), Stage 1 becomes a broadcast, the orders side is not shuffled, and Stages 0 and 2 merge into one.

Say it in an interview
"An action creates a job. The DAG scheduler walks the plan back from the result and starts a new stage at every shuffle dependency, so stages are runs of narrow transformations. Each stage runs one task per partition, so partitions decide parallelism."

reduceByKey vs groupByKey

Both group by key and both shuffle. The difference is how much they shuffle.

groupByKey

Ships every (key, value) pair across the network, then builds the full list of values per key in memory on the reducer.

map side: (a,1) (a,1) (a,1) (b,1)
shuffled: 4 records

A hot key's whole value list must fit in one task's memory → OOM risk.

reduceByKey

Combines values on the map side first (like a Hadoop Combiner), then shuffles one partial result per key per partition.

map side: (a,3) (b,1)
shuffled: 2 records

Less network, less memory. Use it (or aggregateByKey) whenever the function is associative.

With DataFrames you get this automatically: groupBy().agg(sum(...)) plans a partial_sum before the shuffle and a final sum after it. You can see both in explain().

Check yourself

How many jobs: df = spark.read.parquet(p); df.count(); df.filter(...).write.parquet(q)?
At least two, one per action (count and write). The read itself may add a small listing or schema job. Both actions re-read the files unless df is cached.
Where exactly is a stage boundary created?
At every wide (shuffle) dependency, shown as Exchange in the physical plan. Narrow operations on either side are pipelined into the same stage.
Is coalesce narrow or wide?
Narrow. It merges existing partitions without a shuffle. repartition is wide. Module 4 covers the performance consequences.
Why is a join sometimes narrow?
With a broadcast join, the small table is copied to every executor and the large side is joined in place, so the large side needs no shuffle. Pre-bucketed tables on the join key also avoid the shuffle.
What does Spark do if a task fails?
The task scheduler retries it (default spark.task.maxFailures=4). If shuffle output from a previous stage is lost (executor died), the parent stage's affected tasks are recomputed from lineage.
